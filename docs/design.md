# Hikae 詳細設計書（非エンジニア向け GUI Git ツール）

Oct 7, 2026 · @shiki

## 0. 確定済みの前提

本アプリは「1人のユーザーが、自分のファイルを GitHub 上に安全に置き、過去の状態へいつでも戻せる」ことに特化します。以下はヒアリングで確定した事項で、以降の章はすべてこれを前提にしています。

| 論点 | 決定 | 主な影響 |
| --- | --- | --- |
| 対象 OS | Windows / macOS | Tauri で WebView2 と WKWebView の2系統を検証 |
| 基盤 | Tauri 2 + SvelteKit（Svelte 5）+ Master CSS（rc） | Rust 側に Git・LLM・ファイル監視を集約 |
| リモート | GitHub のみ | 認証・リポジトリ作成・所有者一覧を GitHub API に一本化 |
| 利用形態 | 1人で複数 PC 間の同期・バックアップ | 競合は「自分の別 PC との不一致」として扱う |
| 自動保存 | 隠し ref（`refs/snapshots/*`）にローカル記録。手動の「保存」のみ通常 commit | 公開履歴を書き換えずに細かい復元点を持てる |
| 取り込み方式 | merge 固定（fast-forward 優先）。rebase は UI に出さない | 設定項目から merge/rebase の選択を削除 |
| 作業コピー（ブランチ） | MVP 対象外。Phase 3 で対応 | MVP は単一ブランチ前提 |
| 所有者切り替え | GitHub アカウントは1つ。リポジトリ作成・一覧で「個人／Organization」を選ぶ | 認証の多重化は不要 |
| .gitignore で追跡中ファイルを除外 | 「今後の変更だけ無視」「履歴に残したまま追跡を外す」を選択式 | 6章で詳細化 |
| ローカル LLM | 任意機能。アプリ内でモデル DL、詳細設定から Ollama に切替可。一般的なノート PC も対象 | ルールベース生成を主、LLM を補強とする |
| プレビュー拡張 | 当面は自作のみ。将来は第三者作成も視野。作成者はエンジニア想定 | 拡張 API を最初から公開前提の形で切る |
| Office 比較 | docx/xlsx はテキスト抽出して差分表示 | ZIP 内 XML のパーサを内蔵 |

アプリ名は **Hikae**（控え）とします。配布サイトは shiki-01.com のサブドメインに置きます。GitHub のユーザー名 `hikae` は第三者が取得済みのため、Organization やリポジトリは別名（例: `hikae-app`）で作成します。npm と crates.io の `hikae` は 2026-10-07 時点で未使用です。

## 1. 要件定義

対象は「Git を知らないが、ファイルを失いたくない・前の版に戻したい」個人です。成功条件は、初回起動から最初のアップロードまでを Git 用語なしで5分以内に終えられることです。

### 1.1 ユーザー像

| ペルソナ | 管理対象 | 主な動機 | 技術水準 |
| --- | --- | --- | --- |
| 学生・研究者 | レポート、論文（docx）、スライド、データ（xlsx/csv） | 締切前の版に戻したい、PC 故障に備えたい | ファイル操作はできる。ターミナルは使わない |
| 創作者 | イラスト（png/psd）、小説原稿（txt/md）、設定資料 | 過去の版との見比べ、2台の PC での作業 | 同上 |
| 事務職 | 書類テンプレート、表計算 | 誰がいつ何を変えたかではなく「いつ何が変わったか」を見たい | 同上 |

### 1.2 ユースケース

1. 既存フォルダを「見守り対象」にし、GitHub に非公開でバックアップする
2. 作業の区切りで「保存」し、メッセージは提案文をそのまま使う
3. 数日前の版と現在を見比べ、1ファイルだけ前の版に戻す
4. 別の PC で同じフォルダを取り込み、続きから作業する
5. 2台で別々に編集してしまった差分を「どちらの版を使うか」で解消する
6. 誤って消したファイルを、自動保存（スナップショット）から復元する
7. アプリから新しいリポジトリを作り、個人または所属 Organization に置く

### 1.3 機能要件

| ID | 機能 | 要件の要点 | フェーズ |
| --- | --- | --- | --- |
| F1 | 保存 | 変更全件を自動対象化。メッセージ自動提案。1クリック | MVP |
| F2 | 履歴 | タイムライン表示。各時点のファイル一覧と内容表示 | MVP |
| F3 | 比較 | 任意2時点／現在。テキスト行差分、画像の並列・重ね合わせ、docx/xlsx はテキスト抽出差分 | MVP（画像・Office は Phase 2） |
| F4 | 元に戻す | ファイル単位／全体。影響範囲表示。実行前の状態を自動保存 | MVP |
| F5 | 作業コピー | 一覧から切り替え。未保存変更は自動退避 | Phase 3 |
| F6 | 最新を取り込む | fetch+merge を1ボタン化。起動時・定期の自動取り込み | MVP |
| F7 | アップロード | 手動、または保存時に自動 | MVP |
| F8 | 変更のぶつかり解消 | 自分の版／相手の版の2択。テキストのみ行単位編集 | MVP（2択）、Phase 2（行単位） |
| F9 | 自動保存 | ファイル監視で隠し ref にスナップショット | Phase 2 |

### 1.4 非機能要件

- **安全性**: アプリの全操作は、操作前の状態へ復元可能であること。リモートへの force push は内部でも行わない
- **性能**: 1万ファイル・合計 5GB のリポジトリで、状態表示が 1 秒以内に更新されること（`git status` の untracked キャッシュ利用を前提）
- **起動**: コールドスタート 2 秒以内（LLM はアイドル時遅延ロード）
- **配布サイズ**: LLM・git バイナリを除くインストーラ 30MB 以下
- **オフライン**: 保存・履歴・比較・元に戻すはネットワークなしで動作すること
- **互換性**: 作られるリポジトリは標準の Git で読めること。独自形式はアプリ設定と隠し ref のみ
- **機密情報**: トークンは OS のキーチェーン（Windows Credential Manager / macOS Keychain）に保存し、平文ファイルに書かない
- **言語**: 初期は日本語 UI。文言は i18n キー化して英語追加に備える

### 1.5 スコープ外

- GitHub 以外のホスティング（GitLab、Bitbucket、自前サーバ）
- 複数人での共同編集を前提とした機能（レビュー、Pull Request、担当者表示）
- rebase、cherry-pick、tag、submodule、stash の直接操作
- 履歴の書き換え（commit の修正・削除・squash）
- Linux 版（Tauri なので技術的には可能だが、検証・配布はしない）
- 1ファイル 2GB を超えるファイルの管理

## 2. 用語設計

画面上には Git 用語を一切出しません。例外はエラー詳細の「技術情報を表示」欄のみで、サポート時の手がかりとして原文を残します。

### 2.1 対応表

| Git 用語 | 画面上の表現 | 補足・見せ方 |
| --- | --- | --- |
| repository | プロジェクト | 「見守っているフォルダ」と説明する |
| working tree の変更 | 未保存の変更 | 件数バッジで常時表示 |
| commit | 保存（保存ポイント） | タイムライン上の点。名詞は「保存ポイント」 |
| commit message | メモ | 「この保存のメモ」 |
| staging / index | （出さない） | 常に全件対象 |
| log / history | 履歴 | 縦のタイムライン |
| diff | 比較 | 「見比べる」ボタン |
| HEAD | 現在 | 「いまのファイル」 |
| branch | 作業コピー | Phase 3。「別の案を試す場所」と説明 |
| checkout / switch | 切り替える | 同上 |
| revert / restore | 元に戻す | ファイル単位は「この版に戻す」 |
| push | アップロード | クラウドアイコン＋状態 |
| fetch + pull | 最新を取り込む | 1ボタン |
| conflict | 変更のぶつかり | 「2台で別々に変更された」と説明 |
| remote（origin） | クラウドの保管場所 | GitHub の名前は出してよい（ログインで必要なため） |
| .gitignore | 保存しないファイル | 除外設定画面 |
| 自動スナップショット（独自 ref） | 自動保存 | 「保存ポイント」とは別の小さな点で表示 |
| ahead / behind | アップロード待ち n 件／取り込み待ち n 件 | 数値ではなく文で表示 |
| Organization | 保存先（個人 / チーム名） | リポジトリ作成時のみ |

### 2.2 概念の見せ方の方針

- **状態は3つだけ見せる**: 「すべて保存済み」「未保存の変更あり」「クラウドと差あり（アップロード待ち／取り込み待ち）」。この3状態をヘッダーの1行で表す
- **保存ポイントと自動保存を区別する**: 保存ポイントは本人が意図した区切り、自動保存は保険。タイムラインでは自動保存を既定で折りたたむ
- **クラウドは「控え」として見せる**: 「アップロード＝クラウドに控えを置く」。push/pull の方向性は矢印アイコンで補う
- **「元に戻す」は過去を消さない**: 戻した後も履歴は残り、「戻す操作」自体が新しい保存ポイントとして積まれることをダイアログで明示する
- **動詞を統一する**: ボタンは「保存する」「見比べる」「元に戻す」「取り込む」「アップロードする」の5動詞を中心にする

## 4. 主要操作フローと Git コマンド対応

すべての状態変更操作は「操作前に復元点を作る → 本処理 → 失敗時は復元点へ戻す」という同じ枠で実装します。復元点の作り方は6章で定義し、ここでは `snapshot()` と表記します。コマンドは git CLI 前提で記載します（8章の推奨構成）。

### 4.1 保存

1. 事前検査: 新規・変更ファイルのサイズを確認（50MB 超で警告、100MB 超は保存不可として5章の文言を表示）
2. `git add -A`（.gitignore を尊重。ステージングは常に全件）
3. メモの提案: `git diff --cached --name-status -M` の結果からルールベースで生成（10章）。LLM 有効時は非同期で差し替え候補を出す
4. `git -c core.hooksPath= commit -m <メモ>`（ユーザー環境の hook による予期しない失敗を避ける）
5. 「保存時に自動アップロード」がオンなら 4.5 を実行

署名（`user.name` / `user.email`）はリポジトリ単位で、GitHub のユーザー名と noreply アドレス（`<id>+<login>@users.noreply.github.com`）を設定します。本名やメールアドレスを公開リポジトリに残さないためです。

### 4.2 元に戻す

Git の `revert`（特定の保存を打ち消す新しい保存を作る）は使いません。「ある時点の状態にする」ほうが非エンジニアの直感に合い、競合も起きないためです。

1. 影響範囲の算出: `git diff --name-status <時点> -- <対象>`（現在との差）を D2 に表示
2. `snapshot()` で現在の作業状態（未保存変更を含む）を自動保存として記録
3. ファイル単位: `git restore --source=<時点> --worktree --staged -- <path>`。その時点に存在しないファイルは削除扱い
4. 全体: `git restore --source=<時点> --worktree --staged :/`（その時点に無い追跡ファイルは削除される。未追跡ファイルは残す）
5. 「戻した後に自動で保存」（初期値オン）なら、メモ「10/4 18:02 の状態に戻しました（3件）」で commit
6. 取り消しは、トーストの「取り消す」から手順2の自動保存へ同じ手順で戻す

### 4.3 最新を取り込む

1. 未保存の変更がある場合: `snapshot()` 後、「取り込む前に自動で保存」（初期値オン）なら 4.1 で commit。オフなら確認ダイアログ
2. `git fetch --prune origin`
3. `git rev-list --left-right --count HEAD...@{u}` でアップロード待ち／取り込み待ちを算出
4. 取り込み待ちのみ: `git merge --ff-only @{u}`
5. 双方に差がある: `git update-ref refs/<app>/backup/pre-merge/<時刻> HEAD` の後、`git merge --no-edit @{u}`
6. 競合なし → 完了。競合あり → 4.4
7. 自動アップロードがオンなら 4.5
8. 追加処理: 取り込みで「除外設定により相手側で追跡を外されたファイル」が削除される場合、マージ前の内容を作業フォルダに書き戻す（4.8 の注意点への対策）

### 4.4 変更のぶつかり解消

1. 対象一覧: `git status --porcelain=v2` の `u` 行（両方変更／片方削除を区別）
2. 「この PC の版」: `git checkout --ours -- <path>`、「クラウドの版」: `git checkout --theirs -- <path>`
3. 「使わなかった版を別名で残す」: `git show :3:<path>`（または `:2:`）の内容を `<名前> (クラウドの版 MM-DD).<拡張子>` として書き出す
4. 片方が削除している場合: 「残す」／「削除を受け入れる」の2択（`git add` または `git rm`）
5. 行単位編集（テキストのみ、Phase 2）: `:1:`（共通の元）、`:2:`、`:3:` を取得し、アプリ内の3ペインで組み立てて書き込む
6. 全件解消後: `git add <paths>` → `git commit --no-edit`（メモは「2台の変更をまとめました」に置換）
7. 「あとで」: `git merge --abort`。復元点 `pre-merge` が残っているので状態は完全に戻る

### 4.5 アップロード

1. `git push origin HEAD`（`--force` 系は内部でも使わない）
2. 拒否（相手側が先に進んでいる）: 4.3 を実行してから1回だけ再試行。再度失敗したらエラー表示
3. upstream 未設定時のみ `git push -u origin HEAD`

### 4.6 リポジトリの作成・取得

| 操作 | GitHub API | Git |
| --- | --- | --- |
| 保存先の一覧 | `GET /user`、`GET /user/orgs` | — |
| 新規作成（個人） | `POST /user/repos`（`private: true` 初期値） | `git init -b main` → `git remote add origin` → 初回保存 → `git push -u` |
| 新規作成（Org） | `POST /orgs/{org}/repos` | 同上 |
| 既存フォルダを登録 | 上記いずれかで空リポジトリを作成 | 既存の `.git` があれば再利用し remote のみ追加 |
| GitHub から取得 | `GET /user/repos?affiliation=owner,organization_member` | `git clone` |

Org に作成権限がない場合は API が 403 を返すため、作成ダイアログで保存先を選んだ時点で `GET /orgs/{org}/memberships/{login}` を確認し、作れない保存先は灰色表示にします。

### 4.7 ファイルの追加・外部で開く

- D&D: Rust 側でプロジェクト内へコピー（移動ではない）。同名がある場合は「置き換える／両方残す（連番）」を選択。コピー直後にサイズ検査を行う
- 既定のアプリで開く: Tauri の opener プラグイン
- VS Code で開く: `vscode://file/<絶対パス>` の URL スキームを使う（`code` コマンドが PATH に無い環境でも動く）。VS Code 未インストールならメニューを非表示
- フォルダで表示: Windows は `explorer /select,`、macOS は `open -R`
- 過去の版を開く: `git show <時点>:<path>` を一時フォルダに書き出し、読み取り専用属性を付けて開く

### 4.8 保存しないファイル（.gitignore）

1. パターンを追加: 拡張子・フォルダ・個別ファイルを GUI で選び、.gitignore に追記して保存
2. `git ls-files -ci --exclude-standard` で「すでに保存対象になっている該当ファイル」を検出
3. 該当があれば次の2択を表示
   1. **今後の変更だけ無視する**: `git update-index --skip-worktree <path>`。クラウドには今の版が残る。設定はこの PC のみ有効なため、アプリ設定に記録し、他の PC で同じプロジェクトを開いたときに再適用を提案する
   2. **保存対象から外す**: `git rm --cached -r <path>` → 保存。PC 上のファイルは残る。過去の保存ポイントには残る
4. 2 を選んだ場合の注意: 他の PC が取り込むと、Git はそのファイルを削除する。4.3 の手順8で書き戻して防ぐ
5. 「過去の履歴からも完全に消す」（パスワード等を誤って保存した場合）は履歴の書き換えが必要なため対象外とし、ヘルプで GitHub のドキュメントへ案内する

## 6. 安全設計・内部バックアップ戦略

安全性は「危険なコマンドを実行層で拒否する」「状態変更の前に必ず復元点を作る」「中断を検出して戻せる」の3層で担保します。UI で隠すだけでは、将来の機能追加やバグで破壊的操作が混入するため、実行層で強制します。

### 6.1 第1層: コマンドの許可リスト

Rust 側の `GitRunner` は、引数を含めて許可リストに一致する呼び出しのみ実行します。以下は呼び出し側のコードに書かれていても実行時に拒否します。

- `push` の `--force` / `--force-with-lease` / `+refspec`、`--delete`、`--mirror`
- `reset --hard`、`clean`、`branch -D`、`checkout -f`、`restore` を `--source` なしで worktree に適用する呼び出し（未保存変更の破棄になるため）
- `rebase`、`filter-branch`、`commit --amend`、`gc --prune=now`、`reflog expire`
- `update-ref -d` は自アプリの名前空間（`refs/<app>/`）以外を拒否

### 6.2 第2層: 復元点（隠し ref）

| 名前空間 | 作成タイミング | 指す先 | 保持期間（初期値） |
| --- | --- | --- | --- |
| `refs/<app>/snapshots/<ブランチ>/<時刻>` | ファイル監視の自動保存、元に戻す前、取り込む前、ぶつかり解消前 | 作業フォルダ全体（未保存変更を含む）の commit | 7日間は全件、30日までは1時間に1件、90日までは1日に1件 |
| `refs/<app>/backup/<操作名>/<時刻>` | merge、restore、除外設定変更の直前 | その時点の HEAD | 90日 |

**スナップショットの作り方**（作業フォルダとインデックスを一切変更しない）:

1. 一時インデックス `GIT_INDEX_FILE=<一時パス>` を `HEAD` から作る（`git read-tree HEAD`）
2. 同じ一時インデックスに `git add -A` → `git write-tree`
3. ツリーが直前のスナップショットと同一なら終了（重複を作らない）
4. `git commit-tree <tree> -p HEAD -m "auto: <時刻>"` → `git update-ref refs/<app>/snapshots/...`

これらの ref は `refs/heads/` の外にあるため、`git push origin HEAD` では送信されず、GitHub 上の履歴にも出ません。整理（間引き）は自アプリの ref の削除のみで行い、実際のデータ削除は Git の通常の `gc`（既定の猶予期間つき）に任せます。

### 6.3 第3層: 操作ジャーナル

- 状態変更操作の開始時に `.git/<app>/journal.json` へ「操作名・開始時刻・復元点の ref・対象パス」を書き、完了時に消す
- 起動時やプロジェクト表示時にジャーナルが残っていれば、E15 として「続きを行う／操作前に戻す」を提示する
- `MERGE_HEAD` や `index.lock` も合わせて検査し、他ツールによる中断と区別する

### 6.4 そのほかの保証

- **未追跡ファイルを消さない**: アプリが作業フォルダからファイルを削除するのは「元に戻す」で、その時点に存在しない追跡ファイルを対象にした場合のみ。その場合も直前にスナップショットがある
- **追跡解除でローカルを消さない**: 4.8 の「保存対象から外す」は `--cached` 固定。他 PC での削除は 4.3 手順8で書き戻す
- **アップロード済みの履歴は変えない**: 公開側の ref を書き換える操作は存在しない
- **復元 UI**: 設定の「詳細」に「自動保存から復元」画面を置き、スナップショットを時刻順に一覧して任意の時点のファイルを取り出せるようにする（最後の砦）
- **自動保存をクラウドにも控える**（Phase 3、初期値オフ）: `refs/<app>/snapshots/*` を明示指定で push する。容量を使うため既定では行わない

## 7. 設定項目と初期値の根拠

初期値は「1人・複数 PC」の利用形態に合わせ、クラウドとの差を常に小さく保つ方向に倒します。差が小さいほど、変更のぶつかりが発生しにくいためです。設定は「アプリ全体」と「プロジェクト別（上書き可）」の2階層です。

| 区分 | 項目 | 選択肢 | 初期値 | 根拠 |
| --- | --- | --- | --- | --- |
| 取り込み | 起動時に取り込む | オン / オフ | オン | 別 PC の作業を先に反映し、ぶつかりを未然に防ぐ |
| 取り込み | 定期的に取り込む | オフ / 5分 / 15分 / 60分 | 15分 | 1人利用では頻繁な取り込みは不要。fetch のみ行い、差がある場合だけ merge する |
| 取り込み | 取り込む前に未保存の変更を保存 | オン / 確認する | オン | 未保存のまま merge すると失敗しやすい。スナップショットも併用する |
| 取り込み | ぶつかり発生時 | すぐ解消画面を開く / 通知だけ出す | 通知だけ出す | 自動取り込み中に突然モーダルが開くと混乱するため |
| 取り込み | 方式 | merge 固定（表示しない） | — | 0章の決定事項。rebase は UI に出さない |
| アップロード | 保存時に自動アップロード | オン / オフ | オン | バックアップ用途の主目的。オフだと PC 故障時に失われる |
| アップロード | アップロード待ちの通知 | オフ / 1時間 / 1日 | 1日 | 自動アップロードをオフにした人への保険 |
| 自動保存 | ファイル監視による自動保存 | オフ / オン | オン | 隠し ref のため履歴を汚さない。誤削除からの復元手段になる |
| 自動保存 | 自動保存の間隔 | 変更後 30秒 / 2分 / 10分 | 2分 | 保存中のファイル（Word の一時ファイル等）を拾わないよう、最後の変更から一定時間静止してから記録する |
| 自動保存 | 保持期間 | 30日 / 90日 / 1年 | 90日 | 6.2 の間引き規則と合わせ、容量増加を抑える |
| 保存 | メモの自動提案 | ルールのみ / AI を使う | ルールのみ | LLM は任意機能のため |
| 保存 | 元に戻した後に自動で保存 | オン / オフ | オン | 戻した結果が未保存のまま残ると、次の取り込みで混乱するため |
| 保存 | 大きいファイルの警告閾値 | 25MB / 50MB / 100MB | 50MB | GitHub は 50MB 超で警告、100MB 超を拒否する |
| 表示 | 自動保存をタイムラインに表示 | 折りたたむ / 表示 / 隠す | 折りたたむ | 保存ポイントを主役にする |
| 外部アプリ | 「開く」の既定動作 | 既定のアプリ / VS Code | 既定のアプリ | 非エンジニアは VS Code を使わない前提 |
| AI | 実行方式 | 内蔵 / Ollama（詳細設定） | 内蔵 | 10章 |
| AI | 使用モデル | 10章の段階から選択 | 未インストール | 初回に容量を確認してから DL させる |
| AI | AI に渡す範囲 | ファイル名のみ / テキスト差分まで / 画像も含める | テキスト差分まで | 10章の段階と連動 |
| 拡張 | 拡張機能の有効化 | 個別にオン / オフ | 同梱分はオン | 11章 |
| 詳細 | git 実行ファイル | 同梱 / システムの git | 同梱 | バージョン差による挙動の違いを避ける |
| 詳細 | 技術情報をエラーに表示 | オン / オフ | オフ | 折りたたみ欄は常にあるため、展開状態の既定のみ |

「取り込み方式」「merge と rebase の選択」は当初の要望にありましたが、0章の決定に基づき設定から外しています。

### 7.1 詳細設定（advanced）

13.2 の論点はすべて推奨案で確定し、ライセンスを除いて次の詳細設定から変更できるようにします。詳細設定は設定画面の最下部に折りたたみで置き、変更時は影響を1文で表示します。

| 項目 | 選択肢 | 初期値 | 対応フェーズ |
| --- | --- | --- | --- |
| 新規リポジトリの既定の公開範囲 | 非公開 / 公開 | 非公開 | Phase 1 |
| 元に戻した後に自動で保存 | オン / オフ | オン（通常設定と同じ項目を再掲） | Phase 1 |
| 自動保存の容量上限 | なし / プロジェクトサイズの 1倍 / 2倍 / 5倍 | 2倍 | Phase 2 |
| AI モデルの指定 | カタログから選ぶ / 任意の GGUF ファイルを指定 | カタログから選ぶ | Phase 2 |
| 作業コピー機能の表示 | オフ / オン | オフ | Phase 3 |
| 拡張機能の開発者モード（署名なしの手動導入） | オフ / オン | オフ | Phase 3 |
| 拡張機能の追加索引 | 公式のみ / URL を追加 | 公式のみ | Phase 4 |
| Git LFS | 無効 / 有効 | 無効 | Phase 4 |

- 「用語の表示」は2章の用語決定に対する逃げ道として追加した項目で、併記時は「保存（commit）」のように括弧で示す
- Git LFS を有効にした場合、既存の履歴にある大きいファイルは移行しない（移行は履歴の書き換えになるため）

## 8. 技術スタック比較と推奨構成

推奨は「Tauri 2 + SvelteKit（Svelte 5）+ Master CSS（rc）、Git 操作は同梱の git CLI、LLM は llama.cpp の `llama-server` をサイドカー起動」です。Git の挙動を本家と完全に一致させることと、LLM やファイル監視の不具合でアプリ本体が落ちないことを優先しました。

### 8.1 Git 操作層の比較

| 候補 | 機能網羅 | 速度 | 認証 | 配布 | 判定 |
| --- | --- | --- | --- | --- | --- |
| git CLI（同梱） | 完全。merge、競合ステージ、LFS も本家どおり | 1回の起動に数十 ms（Windows で遅め）。`-z` / `--porcelain=v2` の解析が必要 | 自作 credential helper でトークンを渡せる | Windows は MinGit、macOS は自前ビルドを同梱（数十 MB） | **採用** |
| libgit2（git2-rs） | 基本操作は可。merge 周りやフック、LFS は非対応または挙動差あり | プロセス起動なしで高速 | コールバックで実装可能 | ライブラリ静的リンクのみ | 不採用（挙動差が安全設計の前提を崩す） |
| gitoxide（gix） | 読み取り系は成熟。書き込み・push は発展途上 | 高速 | 実装途上 | Pure Rust で配布が楽 | Phase 3 で読み取り高速化に検討 |
| isomorphic-git | 限定的。大きいリポジトリで遅い | 遅い | HTTP のみ | JS のみで完結 | 不採用 |

補足: git は GPLv2 のため、同梱時はライセンス文書と入手先を明示します。アプリ本体は別プロセスとして呼び出すだけなので、アプリのライセンスには影響しません。

### 8.2 そのほかの選定

| 領域 | 採用 | 主な代替 | 採用理由 |
| --- | --- | --- | --- |
| 基盤 | Tauri 2 | Electron | 配布サイズ・メモリが小さい。Rust 側に Git・監視・LLM を集約できる。WebView 差異は検証で吸収 |
| UI | SvelteKit（Svelte 5、adapter-static による SPA 構成）+ TypeScript + Master CSS（rc） | React + Tailwind CSS | 開発者の習熟を優先。runes で状態管理が簡潔になり、実行時サイズも小さい。拡張機能の renderer は iframe 内で独立して動くため、本体のフレームワークに左右されない |
| 状態管理 | Svelte 5 runes（UI 状態）+ TanStack Query の Svelte 版（バックエンド由来データ） | runes のみの自前キャッシュ | バックエンドのイベントでキャッシュを無効化する設計と相性が良い |
| 型共有 | tauri-specta | 手書き | Rust のコマンド定義から TS 型を自動生成し、不一致を防ぐ |
| ファイル監視 | notify + notify-debouncer-full | 自前ポーリング | クロスプラットフォームで実績がある |
| 差分表示 | 自作ビュー（git の diff 出力を解析） | Monaco Diff Editor | Monaco は数 MB と重く、編集機能も不要 |
| docx / xlsx 抽出 | zip + quick-xml（docx）、calamine（xlsx） | LibreOffice 変換 | 外部依存なしで段落・セル単位の抽出ができる |
| 認証 | GitHub OAuth App の Device Flow | GitHub App、PAT 手入力 | クライアントシークレット不要でデスクトップアプリに適する。PAT 手入力は非エンジニアに不向き |
| トークン保管 | keyring クレート（OS キーチェーン） | 暗号化ファイル | 1.4 の非機能要件 |
| アプリ内データ | SQLite（rusqlite） | JSON ファイル | プロジェクト登録、スナップショット索引、LLM キャッシュをまとめて扱う |
| LLM 実行 | `llama-server` サイドカー（OpenAI 互換 API） | llama.cpp の Rust バインディングで同一プロセス実行 | メモリ不足で落ちてもアプリ本体は無事。Ollama も OpenAI 互換 API を持つため、接続先 URL の切替だけで両対応できる |
| 配布・更新 | Tauri bundler（Windows: NSIS、macOS: dmg）+ tauri-plugin-updater + GitHub Releases | Microsoft Store、Mac App Store | ストアはサンドボックス制約で任意フォルダ操作・サイドカー実行が難しい |
| 署名 | Windows: コード署名証明書（Azure Trusted Signing 等）、macOS: Developer ID + 公証 | 署名なし | 署名なしだと SmartScreen / Gatekeeper の警告で非エンジニアが離脱する |

**認証の詳細**: スコープは `repo`（非公開リポジトリの読み書き）と `read:org`（所属 Org の一覧）です。git への受け渡しは、アプリ自身を credential helper として登録し（`git -c credential.helper= -c credential.helper="!<アプリ> credential"`）、ユーザーのグローバル git 設定には書き込みません。

### 8.3 モジュール分割

Rust 側は Cargo workspace で機能ごとに crate を分け、Tauri 層（`app`）からのみ組み合わせます。各 crate は Tauri に依存しないため、単体テストと CLI での動作確認が可能です。

| crate / ディレクトリ | 責務 | 依存先 |
| --- | --- | --- |
| `core-git` | `GitRunner`（許可リスト、環境変数、タイムアウト）、出力パーサ | なし |
| `core-safety` | スナップショット、バックアップ ref、操作ジャーナル、間引き | core-git |
| `core-ops` | 保存、元に戻す、取り込み、アップロード、ぶつかり解消、除外設定の各ユースケース | core-git, core-safety |
| `core-watch` | ファイル監視、静止判定、自動保存のスケジュール | core-safety |
| `core-github` | Device Flow、REST API、keyring、credential helper | なし |
| `core-preview` | 種別判定、テキスト／画像／docx／xlsx 抽出、拡張機能ホスト | なし |
| `core-llm` | モデル管理（DL・検証・削除）、サイドカー制御、Ollama 接続、プロンプト生成 | core-preview |
| `core-store` | SQLite、設定、プロジェクト登録 | なし |
| `app` | Tauri コマンド・イベント、スケジューラ、プロジェクト単位の操作キュー | 上記すべて |
| `src/lib/features/*` | projects, changes, history, compare, conflict, settings, ai, extensions | 生成された TS バインディング |

```text
UI（WebView・SvelteKit） ←postMessage→ 拡張 renderer（sandbox iframe）
        │
app（Tauri コマンド・イベント／操作キュー（直列）／スケジューラ）
   │          │            │             │              │            │
core-ops   core-watch   core-github   core-preview    core-llm     core-store
   └────┬─────┘            │             │              │            │
   core-safety           GitHub API    WASM 抽出器     llama-server  SQLite
        │                  │            (wasmtime)     または Ollama
     core-git              │
        │                  │
  git CLI（同梱）            │
        └──────┬───────────┘
      GitHub 上のリポジトリ
```

UI と拡張 renderer は Rust 層を介さずに Git やファイルへ触れられず、状態変更はすべて操作キューから core-safety を経て git CLI に届きます。

**操作キュー**: 同一プロジェクトへの状態変更は `app` 層の直列キューで1件ずつ実行します。自動取り込みと手動保存が同時に走って `index.lock` が衝突する事態を、設計上発生させないためです。読み取り（状態表示、履歴、比較）はキューを通さず並列に実行します。

## 9. データモデル・状態管理

真実の情報源は常に Git リポジトリと Rust 側です。フロントエンドは表示用のキャッシュのみを持ち、バックエンドからのイベントでキャッシュを無効化して再取得します。履歴やファイル内容を SQLite に複製しないことで、外部ツールで操作された場合も表示が食い違いません。

### 9.1 永続データ

| 保存先 | 内容 | 主な項目 |
| --- | --- | --- |
| アプリ設定（OS の設定ディレクトリ、JSON） | アプリ全体の設定 | 7章の全体項目、UI 言語、ウィンドウ状態 |
| SQLite `projects` | 登録プロジェクト | id、パス、表示名、remote URL、所有者（個人／Org 名）、既定ブランチ、最終表示日時、プロジェクト別設定の上書き（JSON） |
| SQLite `snapshots` | スナップショット索引 | project\_id、ref 名、作成日時、理由（監視／元に戻す前／取り込み前など）、変更ファイル数 |
| SQLite `skip_worktree` | 4.8 の「今後の変更だけ無視」の記録 | project\_id、パス、設定日時（他 PC での再適用提案用） |
| SQLite `llm_models` | 導入済みモデル | id、段階、ファイルパス、SHA-256、サイズ、導入日時 |
| SQLite `message_cache` | 生成済みメモ | 差分ツリーの OID、モデル id、生成文（同じ差分で再生成しない） |
| SQLite `extensions` | 拡張機能 | id、バージョン、有効状態、許可済み権限 |
| `.git/<app>/journal.json` | 操作ジャーナル | 6.3 |
| `.git/<app>/project.json` | リポジトリに紐づく識別子 | アプリが作成したか、初回登録日時（フォルダ移動後の再紐づけに使う） |
| OS キーチェーン | GitHub トークン | — |

### 9.2 プロジェクトの状態

ヘッダーの1行表示（2.2）は、次の値から算出します。

| 値 | 取得元 | 更新契機 |
| --- | --- | --- |
| 未保存の変更（件数・一覧） | `git status --porcelain=v2 -z` | ファイル監視イベント（300ms で間引き） |
| アップロード待ち／取り込み待ち | `git rev-list --left-right --count` | 保存、fetch、push の完了 |
| 実行中の操作 | 操作キュー | 操作の開始・進捗・終了イベント |
| ネットワーク状態 | 直近の fetch / API 結果 | 失敗・成功時 |
| 要対応事項 | ジャーナル、`MERGE_HEAD`、未解消のぶつかり | 起動時、操作終了時 |

操作中の状態遷移は次のとおりです。`待機` 以外の状態では状態変更系のボタンを無効化し、操作キューに積まれた件数を表示します。

| 現在の状態 | イベント | 次の状態 |
| --- | --- | --- |
| 待機 | 保存 / 元に戻す / 取り込み / アップロード開始 | 実行中（操作名） |
| 実行中 | 成功 | 待機 |
| 実行中（取り込み） | 競合検出 | ぶつかり解消待ち |
| ぶつかり解消待ち | 解消して保存 / あとで（merge 中止） | 待機 |
| 実行中 | 失敗 | 復元点へ戻したうえで待機（エラー表示） |
| 任意 | アプリ異常終了 → 再起動 | 要対応（E15） |

### 9.3 フロントエンドとの通信

- **コマンド**（UI → Rust、tauri-specta で型生成）: `project_status`、`list_history`、`read_file_at`、`diff`、`save`、`restore`、`sync`、`push`、`resolve_conflict`、`create_repo`、`add_files`、`open_with` など
- **イベント**（Rust → UI）: `status_changed`、`op_progress`、`op_finished`、`sync_state_changed`、`llm_download_progress`、`needs_attention`
- TanStack Query のキーを `[projectId, 種別, 引数]` で統一し、`status_changed` で `[projectId]` 配下を一括無効化する
- 大きいファイルの内容（画像・抽出テキスト）は JSON に載せず、Tauri のカスタムプロトコル（例: `app-blob://<project>/<oid>`）で UI に直接読ませる

## 10. ローカル LLM 設計

LLM が要約できるのは「アプリが取り出した情報」であり、バイナリそのものではありません。docx・xlsx は抽出テキストの差分を渡せば 3〜4B 級で内容に触れた要約ができ、画像は視覚対応モデル（VLM）が必要で、ノート PC では実用の下限付近になります。そのため「AI に渡す範囲」を段階として選ばせ、段階ごとに必要なモデルと PC の条件を表示します。

### 10.1 VS Code との違い

VS Code（GitHub Copilot）のメッセージ生成が自然なのは、クラウド上の大規模モデルを使っているためです。ローカルで同等の自然さを得るには 7B 級以上とメモリ 16GB 程度が目安になり、一般的なノート PC を対象に含める本件の前提とは両立しません。本アプリでは、小型モデルでも品質が安定するよう、入力を構造化し出力形式を制約します（10.4）。

### 10.2 段階と必要条件

下表のサイズ・速度は 4bit 量子化を前提とした目安で、実機での計測により確定させます。

| 段階 | AI に渡す範囲 | 生成例 | モデル規模 | DL 容量の目安 | 推奨メモリ | CPU のみでの応答の目安 |
| --- | --- | --- | --- | --- | --- | --- |
| 0 | なし（ルールのみ） | 第3章.docx を更新、ほか2件 | 不要 | 0 | — | 即時 |
| 1 | ファイル名・変更種別・件数 | 第3章の更新と図の追加 | 1〜2B | 約 1〜1.5GB | 8GB | 数秒 |
| 2 | 上記＋テキスト差分＋docx/xlsx の抽出差分 | 第3章の実験回数を5回に修正し、追加実験の結果を追記 | 3〜4B | 約 2〜3GB | 8GB（16GB 推奨） | 10〜30秒 |
| 3 | 上記＋画像（変更前後） | 図4に棒グラフを追加 | 3〜4B 級の VLM | 約 3〜5GB | 16GB | 30秒以上 |
| 4 | 段階2と同じ範囲を高品質に | 段階2より自然な文、複数行の要約 | 7〜9B | 約 5〜6GB | 16GB 以上（GPU または Apple Silicon 推奨） | GPU なしでは実用外 |

- 推奨は段階2です。docx・xlsx・テキストの変更内容に触れられ、8GB の PC でも動作します。段階1はルールベースとの差が小さく、導入の価値が限定的です
- 段階3は Phase 3 とし、画像は「追加・削除・差し替え」の事実だけならルールで十分なことを UI で示します
- PDF・psd・動画などは、抽出器がない限りどの段階でもファイル名と種別の情報のみになります。11章の拡張機能が抽出器を提供すれば、段階2の入力に加わります
- 具体的なモデル名は実装時点で日本語の要約品質を評価して決めます。カタログを外部 JSON として配信し、アプリ更新なしで差し替えられるようにします

### 10.3 ルールベース生成（段階0、常に動作）

| 条件 | 生成文 |
| --- | --- |
| 1ファイルの変更 | `<ファイル名> を更新` / `を追加` / `を削除` / `<旧名> を <新名> に名前変更` |
| 同種のファイルのみ複数 | `画像を3件追加`、`文書を2件更新` |
| 混在 | 最も変更量の大きいファイル名 ＋ `ほか n 件` |
| 元に戻す操作 | `<日時> の状態に戻しました（n 件）` |
| ぶつかり解消 | `2台の変更をまとめました` |

### 10.4 生成の仕組み

1. 保存欄には常にルールベースの文を先に入れる。LLM の結果は「✨ 提案」として横に並べ、採用はユーザーが押したときのみ。保存操作は LLM を待たない
2. 入力の構造化: 変更ファイルを「種別・ファイル名・変更量」の表として渡し、差分本文はファイルごとに上限を設けて切り詰める（全体で約 2,000 トークン）
3. 出力の制約: `llama-server` の JSON Schema 制約（Ollama は `format` 指定）で `{ "summary": "50字以内", "details": ["…"] }` の形を強制し、小型モデルの書式崩れを防ぐ
4. タイムアウト（段階2で 30秒）・不正出力・プロセス異常終了時はルールベースのまま何も表示しない（E19 は設定画面でのみ表示）
5. 同じ差分（ツリーの OID）に対する結果は `message_cache` から返す

### 10.5 モデル管理と実行

- **導入**: 設定の AI タブで段階を選ぶ → PC のメモリ・空き容量を検査し、条件を満たさない段階は理由つきで灰色表示 → DL（再開対応、SHA-256 検証）→ アプリのデータフォルダに配置
- **起動と解放**: 生成が必要になった時点で `llama-server` を起動し、5分間使わなければ終了してメモリを解放する
- **GPU**: macOS は Metal、Windows は CPU 版を既定とし、Vulkan 版を詳細設定で選べるようにする（GPU ドライバ依存の不具合を既定値で踏まないため）
- **Ollama への切替**（詳細設定）: 接続先 URL（初期値 `http://localhost:11434`）を指定し、Ollama 側のモデル一覧から選ぶ。通信は OpenAI 互換 API で共通化しているため、`core-llm` 内の分岐は接続先とモデル一覧の取得のみ
- **プライバシー**: 内蔵・Ollama のいずれも PC 内で完結し、ファイル内容は外部へ送信しない。Ollama の接続先に外部ホストが指定された場合は警告を出す

## 11. プレビュー拡張機能の設計

拡張機能は「表示を担う UI（サンドボックス iframe）」と「内容を取り出す抽出器（WASM）」の2種類に分け、どちらもファイルやネットワークに直接触れられない形にします。当面は自作のみですが、最初から第三者向けと同じ境界で作れば、公開時に作り直しが要りません。組み込みのプレビュー（テキスト、画像、docx、xlsx）も同じ API で実装し、API の不足を自分で先に踏みます。

### 11.1 構成

| 種類 | 役割 | 実行環境 | 入力 | 出力 | 制限 |
| --- | --- | --- | --- | --- | --- |
| 表示（renderer） | 1時点の表示、2時点の比較表示 | `sandbox="allow-scripts"` の iframe（同一オリジン不可）、`ext://<id>/` から配信 | `postMessage` で受け取るファイルのバイト列と種別 | 描画のみ | CSP で `connect-src 'none'`。Tauri の IPC に届かない |
| 抽出器（extractor） | 比較用テキスト・LLM 入力の生成 | Rust 側の wasmtime（WASI、ファイル・ネットワークなし） | ファイルのバイト列 | テキストまたは構造化 JSON（段落、セル、ページ） | メモリ 256MB、実行 10秒 |

抽出器を WASM にする理由は、作者が Rust・Go・C など任意の言語で書けること、ネイティブコードを配布させずに済むこと、異常終了してもアプリを巻き込まないことです。

### 11.2 マニフェスト

```json
{
  "id": "example.pdf-preview",
  "name": "PDF プレビュー",
  "version": "1.0.0",
  "apiVersion": "1",
  "contributes": {
    "renderers": [
      { "fileTypes": [".pdf"], "modes": ["view", "compare"], "entry": "ui/index.html" }
    ],
    "extractors": [
      { "fileTypes": [".pdf"], "output": "paragraphs", "entry": "extract.wasm" }
    ]
  },
  "permissions": []
}
```

- `modes` に `compare` がない場合、アプリが `view` を2つ並べて比較画面を作る
- 抽出器の `output` が `paragraphs` / `cells` / `pages` のいずれかなら、アプリ側の行差分・セル差分ビューと LLM 入力（10章 段階2）にそのまま使える
- `permissions` は将来の拡張用に予約（例: 外部フォント読み込み）。初期は空のみ受け付ける

### 11.3 段階的な公開

| フェーズ | 内容 |
| --- | --- |
| Phase 2 | 組み込みプレビューを拡張 API 上で実装（API は非公開） |
| Phase 3 | フォルダまたは zip から手動インストール（開発者モード）。雛形を生成する CLI と型定義パッケージを用意 |
| Phase 4 | GitHub リポジトリ上の索引 JSON を拡張機能一覧として表示。ed25519 署名の検証、権限の事前表示、API バージョン N と N-1 の互換維持 |

### 11.4 採用しなかった案

- **拡張の JS をメイン WebView で実行**: Tauri の IPC に到達でき、ファイル削除や push も呼べるため不採用
- **Node.js ベース（VS Code 型）**: Tauri には Node が無く、同梱すると配布サイズの利点が消えるため不採用
- **ネイティブの動的ライブラリ**: OS・CPU ごとのビルドが必要で、異常時にアプリごと落ちるため不採用

## 12. 開発ロードマップ

MVP は「1台目で保存・履歴・元に戻す、2台目で取り込む」が安全に回るところまでに絞ります。自動保存・画像比較・LLM は MVP の利用感を見てから載せる Phase 2 です。各フェーズの終了条件を満たすまで次へ進まない運用とします。

| フェーズ | 範囲 | 終了条件 |
| --- | --- | --- |
| Phase 0 技術検証 | Tauri の Windows / macOS ビルド、git 同梱と credential helper、Device Flow、一時インデックスでのスナップショット、競合ステージの取得 | 2台の PC 間で「保存 → アップロード → 取り込み → 競合 → 2択解消」が CLI レベルで通る |
| Phase 1 MVP | S0〜S4、D1〜D4、保存、履歴、テキスト比較、元に戻す、取り込み（起動時・定期）、アップロード（自動・手動）、2択の競合解消、リポジトリ作成・取得、D&D、外部で開く、ルールベースのメモ、安全設計の3層、署名と自動更新 | Git 未経験者 5 人が、説明なしで初回アップロードまで 5 分以内に到達し、別 PC での取り込みを完了できる |
| Phase 2 | ファイル監視の自動保存、画像比較、docx / xlsx の抽出差分、行単位の競合解消、保存しないファイルの GUI、ローカル LLM（段階1〜2、Ollama 切替）、組み込みプレビューの拡張 API 化 | 1か月の自己利用で、データ消失・復元不能の事例がゼロ |
| Phase 3 | 作業コピー（ブランチ）、拡張機能の開発者モード、LLM 段階3（画像）、自動保存のクラウド控え、gix による履歴読み取りの高速化 | 第三者が雛形から拡張機能を1つ作成・導入できる |
| Phase 4 | 拡張機能の一覧・署名検証、英語 UI、Git LFS 対応の要否判断 | 利用者の要望とリスク評価に基づき個別判断 |

Phase 1 で特に工数を見込むべき箇所は、Windows でのファイルロック（E12）、改行コード・文字コードの扱い、Gatekeeper / SmartScreen を含む配布の3点です。いずれも Phase 0 で一度通しておくことを推奨します。

## 13. リスクと判断が必要な論点

最大のリスクは、Git がファイルを「バックアップ」ではなく「ソースコード」として扱う既定動作（改行変換、巨大ファイルの扱い、追跡解除時の削除）です。これらは既定値を明示的に上書きして封じます。

### 13.1 設計上のリスク

| リスク | 影響 | 対策 |
| --- | --- | --- |
| 改行コードの自動変換 | Windows と macOS の間でファイル内容が書き換わり、「変更していないのに変更あり」が出る | リポジトリ作成時に `core.autocrlf=false` を設定し、バイト列をそのまま保存する（バックアップ用途として正しい挙動） |
| 日本語ファイル名 | macOS の NFD 正規化で別ファイル扱い、出力の引用符エスケープで解析失敗 | `core.precomposeUnicode=true`、出力は常に `-z` 形式で解析 |
| 大きいファイルでリポジトリが肥大化 | GitHub の制限、clone の長時間化。一度保存すると履歴から消せない | 保存前の検査（E07〜E09）、Phase 4 まで LFS は入れない |
| Office の一時ファイル（`~$*.docx` 等）の混入 | 不要な変更・削除が履歴に残る | 初期の .gitignore テンプレートに OS・Office の一時ファイルを含める |
| クラウド同期フォルダ（OneDrive、iCloud）上のプロジェクト | 同期ソフトが `.git` を書き換え、リポジトリが破損する | 登録時にパスを検査して警告。E10 の復旧手順を用意 |
| ファイル監視の負荷 | 大きなフォルダで CPU 使用率が上がる | `.git` と除外対象を監視から外す。静止判定で間引く |
| skip-worktree の限界（4.8） | 取り込みで該当ファイルが更新されると merge が失敗する | 取り込み前に一時解除 → 内容退避 → 再設定、の手順を `core-ops` に実装 |
| Org の OAuth アクセス制限 | Org のリポジトリにアクセスできない | E02 の文言と、管理者向け説明文のコピー機能 |
| 署名・公証のコスト | 年間費用と手続き | Phase 0 で手続きを開始。未署名の開発版は自分用に限定 |
| WebView の差異 | Windows と macOS で表示や D&D の挙動が異なる | 両 OS での E2E テストを Phase 1 の CI に含める |

- **Master CSS が rc 版である点**: 採用時点の rc 版にバージョンを固定して運用し、正式版への追従は必須としない（lockfile で固定）

### 13.2 判断が必要な論点

| 論点 | 選択肢 | 推奨 | 決める時期 |
| --- | --- | --- | --- |
| 新規リポジトリの公開範囲の既定 | 非公開 / 公開 | 非公開（誤公開の被害が大きいため） | Phase 1 着手前 |
| Git LFS | 対応しない / Phase 4 で任意対応 | 当面対応しない。LFS は無料枠が小さく、容量超過時の挙動が非エンジニアに説明しにくい | Phase 4 |
| 自動保存の保持期間と容量上限 | 期間のみ / 期間＋容量上限 | 期間＋容量上限（例: プロジェクトサイズの 2 倍）。上限超過時は古い順に間引く | Phase 2 着手前 |
| 「元に戻した後に自動で保存」の既定 | オン / オフ | オン（7章） | Phase 1 のユーザーテスト後に再評価 |
| アプリ名・用語の最終決定 | 「保存ポイント」等の候補 | 2章の対応表をユーザーテストで検証 | Phase 1 のユーザーテスト |
| LLM の具体的なモデル | 実装時点の小型モデル | 日本語のメモ生成で 3〜4 候補を比較評価 | Phase 2 着手時 |
| 作業コピー（ブランチ）の見せ方 | 一覧切替 / 「別の案を試す」専用フロー | Phase 3 で再設計（MVP の利用状況を見て、そもそも必要かを含めて判断） | Phase 3 着手前 |
| 拡張機能の配布元 | 自前の索引 / GitHub トピック検索 | 自前の索引（署名と審査の主体を明確にするため） | Phase 4 |
| ライセンス | OSS / プロプライエタリ | アプリ本体のライセンスを Phase 1 公開前に決定（git 同梱の GPLv2 表示は必須） | Phase 1 公開前 |

上記はすべて推奨案で確定しました。ライセンス以外は 7.1 の詳細設定で変更できます。
