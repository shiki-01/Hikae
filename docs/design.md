## 0. 確定済みの前提

本アプリは「1人のユーザーが、自分のファイルを GitHub 上に安全に置き、過去の状態へいつでも戻せる」ことに特化します。以下はヒアリングで確定した事項で、以降の章はすべてこれを前提にしています。

| 論点 | 決定 | 主な影響 |
| --- | --- | --- |
| 対象 OS | Windows / macOS | Tauri で WebView2 と WKWebView の2系統を検証 |
| 基盤 | Tauri 2 + SvelteKit（Svelte 5）+ Master CSS（rc） | Rust 側に Git・LLM・ファイル監視を集約 |
| リモート | GitHub のみ | 認証・リポジトリ作成・所有者一覧を GitHub API に一本化 |
| 利用形態 | 1人で複数 PC 間の同期・バックアップ | 競合は「自分の別 PC との不一致」として扱う |
| 自動保存 | 隠し ref（`refs/snapshots/*`）にローカル記録。手動の「保存」のみ通常 commit | 公開履歴を書き換えずに細かい復元点を持てる |
| 取り込み方式 | merge 固定（fast-forward 優先）。rebase は UI に出さない | 設定項目から merge/rebase の選択を削除 |
| 作業コピー（ブランチ） | MVP 対象外。Phase 3 で対応 | MVP は単一ブランチ前提 |
| 所有者切り替え | GitHub アカウントは1つ。リポジトリ作成・一覧で「個人／Organization」を選ぶ | 認証の多重化は不要 |
| .gitignore で追跡中ファイルを除外 | 「今後の変更だけ無視」「履歴に残したまま追跡を外す」を選択式 | 6章で詳細化 |
| ローカル LLM | 任意機能。アプリ内でモデル DL、詳細設定から Ollama に切替可。一般的なノート PC も対象 | ルールベース生成を主、LLM を補強とする |
| プレビュー拡張 | 当面は自作のみ。将来は第三者作成も視野。作成者はエンジニア想定 | 拡張 API を最初から公開前提の形で切る |
| Office 比較 | docx/xlsx はテキスト抽出して差分表示 | ZIP 内 XML のパーサを内蔵 |

アプリ名は **Hikae**（控え）とします。配布サイトは shiki-01.com のサブドメインに置きます。GitHub のユーザー名 `hikae` は第三者が取得済みのため、Organization やリポジトリは別名（例: `hikae-app`）で作成します。npm と crates.io の `hikae` は 2026-10-07 時点で未使用です。

## 1. 要件定義

対象は「Git を知らないが、ファイルを失いたくない・前の版に戻したい」個人です。成功条件は、初回起動から最初のアップロードまでを Git 用語なしで5分以内に終えられることです。

### 1.1 ユーザー像

| ペルソナ | 管理対象 | 主な動機 | 技術水準 |
| --- | --- | --- | --- |
| 学生・研究者 | レポート、論文（docx）、スライド、データ（xlsx/csv） | 締切前の版に戻したい、PC 故障に備えたい | ファイル操作はできる。ターミナルは使わない |
| 創作者 | イラスト（png/psd）、小説原稿（txt/md）、設定資料 | 過去の版との見比べ、2台の PC での作業 | 同上 |
| 事務職 | 書類テンプレート、表計算 | 誰がいつ何を変えたかではなく「いつ何が変わったか」を見たい | 同上 |

### 1.2 ユースケース

1. 既存フォルダを「見守り対象」にし、GitHub に非公開でバックアップする
2. 作業の区切りで「保存」し、メッセージは提案文をそのまま使う
3. 数日前の版と現在を見比べ、1ファイルだけ前の版に戻す
4. 別の PC で同じフォルダを取り込み、続きから作業する
5. 2台で別々に編集してしまった差分を「どちらの版を使うか」で解消する
6. 誤って消したファイルを、自動保存（スナップショット）から復元する
7. アプリから新しいリポジトリを作り、個人または所属 Organization に置く

### 1.3 機能要件

| ID | 機能 | 要件の要点 | フェーズ |
| --- | --- | --- | --- |
| F1 | 保存 | 変更全件を自動対象化。メッセージ自動提案。1クリック | MVP |
| F2 | 履歴 | タイムライン表示。各時点のファイル一覧と内容表示 | MVP |
| F3 | 比較 | 任意2時点／現在。テキスト行差分、画像の並列・重ね合わせ、docx/xlsx はテキスト抽出差分 | MVP（画像・Office は Phase 2） |
| F4 | 元に戻す | ファイル単位／全体。影響範囲表示。実行前の状態を自動保存 | MVP |
| F5 | 作業コピー | 一覧から切り替え。未保存変更は自動退避 | Phase 3 |
| F6 | 最新を取り込む | fetch+merge を1ボタン化。起動時・定期の自動取り込み | MVP |
| F7 | アップロード | 手動、または保存時に自動 | MVP |
| F8 | 変更のぶつかり解消 | 自分の版／相手の版の2択。テキストのみ行単位編集 | MVP（2択）、Phase 2（行単位） |
| F9 | 自動保存 | ファイル監視で隠し ref にスナップショット | MVP（Phase 2 から前倒し） |

| F14 | 除外設定 | .gitignore を GUI で編集。追跡中ファイルの扱いを選択 | Phase 2 |

### 1.4 非機能要件

- **安全性**: アプリの全操作は、操作前の状態へ復元可能であること。リモートへの force push は内部でも行わない
- **性能**: 1万ファイル・合計 5GB のリポジトリで、状態表示が 1 秒以内に更新されること（`git status` の untracked キャッシュ利用を前提）
- **起動**: コールドスタート 2 秒以内（LLM はアイドル時遅延ロード）
- **配布サイズ**: LLM・git バイナリを除くインストーラ 30MB 以下
- **オフライン**: 保存・履歴・比較・元に戻すはネットワークなしで動作すること
- **互換性**: 作られるリポジトリは標準の Git で読めること。独自形式はアプリ設定と隠し ref のみ
- **機密情報**: トークンは OS のキーチェーン（Windows Credential Manager / macOS Keychain）に保存し、平文ファイルに書かない
- **言語**: 初期は日本語 UI。文言は i18n キー化して英語追加に備える

### 1.5 スコープ外

- GitHub 以外のホスティング（GitLab、Bitbucket、自前サーバ）
- 複数人での共同編集を前提とした機能（レビュー、Pull Request、担当者表示）
- rebase、cherry-pick、tag、submodule、stash の直接操作
- 履歴の書き換え（commit の修正・削除・squash）
- Linux 版（Tauri なので技術的には可能だが、検証・配布はしない）
- 1ファイル 2GB を超えるファイルの管理

## 2. 用語設計

画面上には Git 用語を一切出しません。例外はエラー詳細の「技術情報を表示」欄のみで、サポート時の手がかりとして原文を残します。

### 2.1 対応表

| Git 用語 | 画面上の表現 | 補足・見せ方 |
| --- | --- | --- |
| repository | プロジェクト | 「見守っているフォルダ」と説明する |
| working tree の変更 | 未保存の変更 | 件数バッジで常時表示 |
| commit | 保存（保存ポイント） | タイムライン上の点。名詞は「保存ポイント」 |
| commit message | メモ | 「この保存のメモ」 |
| staging / index | （出さない） | 常に全件対象 |
| log / history | 履歴 | 縦のタイムライン |
| diff | 比較 | 「見比べる」ボタン |
| HEAD | 現在 | 「いまのファイル」 |
| branch | 作業コピー | Phase 3。「別の案を試す場所」と説明 |
| checkout / switch | 切り替える | 同上 |
| revert / restore | 元に戻す | ファイル単位は「この版に戻す」 |
| push | アップロード | クラウドアイコン＋状態 |
| fetch + pull | 最新を取り込む | 1ボタン |
| conflict | 変更のぶつかり | 「2台で別々に変更された」と説明 |
| remote（origin） | クラウドの保管場所 | GitHub の名前は出してよい（ログインで必要なため） |
| .gitignore | 保存しないファイル | 除外設定画面 |
| 自動スナップショット（独自 ref） | 自動保存 | 「保存ポイント」とは別の小さな点で表示 |
| ahead / behind | アップロード待ち n 件／取り込み待ち n 件 | 数値ではなく文で表示 |
| Organization | 保存先（個人 / チーム名） | リポジトリ作成時のみ |

### 2.2 概念の見せ方の方針

- **状態は3つだけ見せる**: 「すべて保存済み」「未保存の変更あり」「クラウドと差あり（アップロード待ち／取り込み待ち）」。この3状態をヘッダーの1行で表す
- **保存ポイントと自動保存を区別する**: 保存ポイントは本人が意図した区切り、自動保存は保険。タイムラインでは自動保存を既定で折りたたむ
- **クラウドは「控え」として見せる**: 「アップロード＝クラウドに控えを置く」。push/pull の方向性は矢印アイコンで補う
- **「元に戻す」は過去を消さない**: 戻した後も履歴は残り、「戻す操作」自体が新しい保存ポイントとして積まれることをダイアログで明示する
- **動詞を統一する**: ボタンは「保存する」「見比べる」「元に戻す」「取り込む」「アップロードする」の5動詞を中心にする

### 3.2 画面遷移

1. 起動 → 初回なら S0 → S1
2. S1 でカード選択 → S2（変更タブ）。タブで S2 ⇄ S3
3. S2 / S3 のファイル行の「見比べる」→ S4。閉じると元のタブへ戻る
4. S2 / S3 の「元に戻す」→ D2 → 完了トースト → S2。S2 の新規ファイルの「元に戻す（作成しない）」→ 確認ダイアログ（4.2。D2 と同じ作り）→ 完了トースト（「取り消す」つき）→ S2
5. ヘッダーの「取り込む」でぶつかり発生 → D3 → 解消後 S2
6. どの画面からも歯車 → S5（S6 / S7 / S8 はその中のタブ）
7. S1 の「＋」→ D1 → 完了後に新しいプロジェクトの S2

### 3.3 ワイヤーフレーム

**S2 プロジェクト画面（変更タブ）**

```text
┌──────────────────────────────────────────────────────────────┐
│ ← 一覧   卒業論文            ● 未保存の変更 3件   ☁ 取り込む  ⚙ │
│                              アップロード待ち 1件 [アップロード] │
├──────────────┬───────────────────────────────────────────────┤
│ [変更] [履歴] │  第3章.docx            [見比べる][元に戻す][開く▾]│
│──────────────│───────────────────────────────────────────────│
│ ✎ 第3章.docx │  （プレビュー：抽出テキスト／画像／差分）        │
│ ＋ 図4.png    │                                               │
│ − 古い案.txt  │                                               │
│              │                                               │
│ ここにファイルを│                                               │
│ ドロップして追加 │                                               │
├──────────────┴───────────────────────────────────────────────┤
│ メモ: [第3章を更新、図4を追加、古い案を削除        ] [✨提案]  │
│                                              [ 保存する ]    │
└──────────────────────────────────────────────────────────────┘
```

- 「開く▾」のメニュー: 既定のアプリで開く / VS Code で開く / フォルダで表示 / パスをコピー
- 左ペイン全体がドロップ領域。ドロップ時は「プロジェクト内のどこに置くか」を最小限のフォルダ選択で聞く
- ✨提案は LLM 有効時のみ表示。無効時もメモ欄にはルールベースの提案が初期入力される
- **ツリー表示**: 左ペインの上部に SegmentedControl「変更のみ」「すべてのファイル」を置く。「すべてのファイル」は、プロジェクトフォルダ全体（保存対象のファイル。保存しないファイルと `.git` は除く）をフォルダ階層で表示し、各ファイルに変更の種類（追加・変更・削除・名前変更・ぶつかり）の小さなバッジを付ける。変更のあるフォルダは最初から開く。クリックすると、変更のあるファイルは右ペインに差分を、変更の無いファイルは種類・サイズ・更新日時と「開く▾」を表示する。実装は 4.1 の補足
- **新規ファイルの「元に戻す（作成しない）」**: 一度も保存されていない新規ファイルの行と、右ペインの操作行には、「元に戻す」の代わりに「元に戻す（作成しない）」を出す。確認ダイアログを経て、ファイルを OS のごみ箱へ移す。実装と安全策は 4.2 の補足
- **「取り込む」ボタン**: 状態表示（5章の優先順位）は 1 つだけだが、別の PC の変更がある（取り込み待ち）ときは、未保存の変更が優先されていても、状態表示とは別に控えめな「取り込む」ボタンを右側に出す（「すべて保存済み」のときの控えめなボタンと同じ見た目）。ぶつかり・途中で止まった操作・大きいファイルによる見送り・処理中・オフライン・再ログインが必要なときは出さない。押したときの動作は 4.3（設定が「確認する」なら E06 の確認）

**D3 変更のぶつかり解消**

```text
┌ 2台で別々に変更されたファイルがあります（2件）─────────┐
│ 第3章.docx                                          │
│   この PC の版   10/6 22:10 保存   [見比べる]         │
│   クラウドの版   10/6 19:40 保存（ノートPC）          │
│   ( ) この PC の版を使う  ( ) クラウドの版を使う       │
│   使わなかった版は「別名で残す」 [✓]                  │
│ ─────────────────────────────────────────────── │
│ メモ.txt   [行ごとに選ぶ…]                           │
│                                [あとで] [解消して保存]│
└───────────────────────────────────────────────────┘
```

- 「別名で残す」は既定オン。使わなかった版を `第3章 (クラウドの版 10-06).docx` としてプロジェクト内に保存し、データ損失感をなくす
- 「あとで」を選んだ場合は merge を中止して元の状態に戻す（6章の安全設計で保証）

## 4. 主要操作フローと Git コマンド対応

すべての状態変更操作は「操作前に復元点を作る → 本処理 → 失敗時は復元点へ戻す」という同じ枠で実装します。復元点の作り方は6章で定義し、ここでは `snapshot()` と表記します。コマンドは git CLI 前提で記載します（8章の推奨構成）。

### 4.1 保存

1. 事前検査（サイズ）: `git status --porcelain=v2 -z -uall --no-renames` で新規・変更されたファイルを 1 件ずつ列挙し、作業フォルダ上のサイズを調べる（保存対象外・未解決の競合・削除・フォルダ・リンクは対象外）
   - 警告閾値（設定 `large_file_warn_mb`、既定 50MB、選択肢 25 / 50 / 100MB）を**超える**ものは「警告」（E08、保存はできる）。100MB（固定。GitHub の上限）を**超える**ものは「保存不可」（E07）。閾値ちょうどのファイルは対象外
   - 該当があれば、**何も変更せず**（復元点も作らず）保存を見送り、該当ファイルのパスとサイズを構造化した結果として返す（`SaveResult.size_check`。エラーではない）。画面が選択を求め、選択を添えた `save_with_size_choice` で保存をやり直す（`saveWithSizeChoice`）
   - 選択は 2 つ。「そのまま保存」（`accept_warned`。警告のファイルにだけ有効で、保存不可のファイルには使えない）、「保存対象から外す」（`exclude`。検査で見つかったパスだけを指定でき、それ以外は `invalid_input` で拒否する）
2. 復元点: 検査を通ったあと、作業フォルダ・インデックスを変更する前に復元点を作る（6.2。操作名 `save`）
3. 「外す」が選ばれたファイル: `git rm --cached --ignore-unmatch -q -- :(literal)<パス>` で追跡から外し、ルート直下の完全一致パターン（`/<パス>`。特殊文字はエスケープ）を .gitignore へ追記する（既にある行は重複させず、改行コードは既存に合わせる）。作業フォルダのファイルは削除しない（不変条件 6）
4. `git add -A`（.gitignore を尊重。ステージングは常に全件）。外したことでステージの内容が空になった場合は、空の保存を作らず「変更なし」として終える（`git diff --cached --quiet`）
5. `git -c core.hooksPath= commit -m <メモ>`（ユーザー環境の hook による予期しない失敗を避ける）。メモの末尾に空行を挟んで `Hikae-PC: <PC 名>` の 1 行（git のトレーラーと同じ形式）を付ける
   - PC 名は環境変数 `COMPUTERNAME` → `HOSTNAME` → `/proc/sys/kernel/hostname` → `/etc/hostname` → `hostname` コマンド（Windows 以外）の順に取得し、最初の呼び出しで決めて使い回す。取得できなければトレーラーを付けない
   - 制御文字（改行・タブを含む）を除き、前後の空白を削り、**64 文字**で切る。改行を混ぜて別のトレーラーを偽造することはできない。メモが空のときは付けない
   - 履歴・競合情報の取得時にトレーラーを本文から分離して `pc_name` として返す（メモ本文の表示にはトレーラーを含めない）。取り込み前の自動保存（4.3）とぶつかり解消の保存（4.4）にも付く
6. 「保存時に自動アップロード」（設定 `auto_push_after_save`）がオンで commit が作られた場合は、スケジューラが直列キュー経由で 4.5 を実行する（保存コマンドは完了を待たない）

メモの提案（10.3）は保存操作とは独立した読み取り専用の処理で、`git status --porcelain=v2 -z -uall --no-renames` の結果（変更種別とファイルサイズ）からルールベースで作る。`--no-renames` のため、名前変更は検出せず追加と削除として扱う。LLM による差し替え候補は未実装（Phase 2）。

**新規（未追跡）ファイルの差分表示**（`core-ops` の `diff_file`。読み取りのみ）:

- `git diff` は、まだ保存もインデックスへの登録もされていないファイルを出力しない。そのため、「いま」との比較（`diff` の `to` が `current`）で対象が新規ファイルのときは、`git diff` を使わず、作業フォルダのファイルを読んで**全行を「追加」の差分行**（新しい側の行番号は 1 から。末尾の改行は行として数えず、行末の `\r` は除く）として返す。「比較先が `current` で未追跡」だと差分が空になる既知の不具合は、これで解消した
- 新規ファイルの判定: インデックスに無く（`ls-files -z --cached -- :(literal)<パス>` が空）、比べる時点にも存在せず、作業フォルダに実体（フォルダ以外）がある。それ以外は従来どおり `git diff`
- 本文を返さず、種類と大きさだけを返すもの: NUL を含む（バイナリ）ファイルと、シンボリックリンク（リンク先は読まない）は**ファイル情報**（サイズ・更新日時。画面は種類・サイズ・更新日時と「開く」）、**1MB（1,048,576 バイト）を超える**ファイルは**「大きすぎて省略」**（DiffView の状態。サイズだけ）。上限ちょうどは本文を出す。内容が空のファイルは「空の新しいファイルです」を出す。判定から読み込みまでの間に大きくなった場合に備え、上限 + 1 バイトまでしか読まない
- パスは `normalize_project_path`（`..`・絶対パス・ドライブ指定・`.git` 配下・先頭 `:` を拒否）で検査し、読む前に親フォルダを `canonicalize` してプロジェクトの配下であることを確認する（`resolve_entry_in_project`。`resolve_in_project` と違い、最後の成分は解決しない）。**シンボリックリンクはたどらない**（リンクそのものは `symlink_metadata` で見る）。プロジェクト外のパスは `invalid_input` で拒否する

**ツリー表示**（`core-ops` の `project_tree`、Tauri コマンド `list_project_tree(id)`。読み取りのみで直列キューは通さない）:

- 一覧は `git ls-files -z -c -o --exclude-standard`（許可リストに既にあるフラグだけ。許可リストは変更していない）。追跡済み + 未追跡で、`.gitignore` の対象と `.git` の配下は含まない。入れ子のリポジトリ（末尾が `/` の項目）とフォルダとして存在するもの（サブモジュール）はファイルとして扱わない。パスの重複（ぶつかり中のファイルは複数のステージで出る）は除く
- 各ファイルにサイズと更新日時（`symlink_metadata`。リンクはたどらない）と、`list_changes` から得た変更の種類・ぶつかりの印を付ける。削除されたファイルはインデックスに残っていれば一覧に出る（インデックスから外れている場合も、変更の一覧にあれば加える）。サイズは持たない
- 件数の上限は **1 万件**（`PROJECT_TREE_MAX_ENTRIES`）。超えたら打ち切り、`truncated` を立てる（画面は「一部のみ表示しています」と注記する）。打ち切るときも、**変更のあるファイルを先に含め**、残りの枠をそのほかのファイルで埋める
- 画面は、変更のあるフォルダを最初から開き、閉じているフォルダの中身は描画しない（`FileTree`。履歴の「この時点の全ファイル」と共通）。ファイル監視の通知（`files-changed`）でこの一覧も取り直す

署名（`user.name` / `user.email`）はリポジトリ単位（`git config --local`）で、GitHub のユーザー名と noreply アドレス（`<id>+<login>@users.noreply.github.com`）を設定します。本名やメールアドレスを公開リポジトリに残さないためです。実装では、プロジェクトの登録時と、保存の直前（ログイン済みでユーザー情報が分かっているとき）に更新します。未ログインやオフラインでユーザー情報を確認できないときは、保存時は既存の署名を変えず、登録時は固定のローカル用署名（`Hikae` / `hikae@users.noreply.github.com`）にします。

### 4.2 元に戻す

Git の `revert`（特定の保存を打ち消す新しい保存を作る）は使いません。「ある時点の状態にする」ほうが非エンジニアの直感に合い、競合も起きないためです。

1. 影響範囲の算出: `git diff --name-status <時点> -- <対象>`（現在との差）を D2 に表示
2. `snapshot()` で現在の作業状態（未保存変更を含む）を自動保存として記録
3. ファイル単位: `git restore --source=<時点> --worktree --staged -- <path>`。その時点に存在しないファイルは削除扱い
4. 全体: `git restore --source=<時点> --worktree --staged :/`（その時点に無い追跡ファイルは削除される。未追跡ファイルは残す）
5. 「戻した後に自動で保存」（初期値オン）なら、メモ「10/4 18:02 の状態に戻しました（3件）」で commit
6. 取り消しは、トーストの「取り消す」から手順2の自動保存へ同じ手順で戻す

実装の補足:

- 全体を戻す操作は `git restore --source=<時点> --staged --worktree -- :`、ファイル単位は `restore_file`（操作名 `restore-file`）。どちらも実行前に復元点を作り、取り消し用の復元点の ref を返す。取り消し（`undo_restore`）は `refs/hikae/snapshots/` か `refs/hikae/backup/` の ref、または完全な OID だけを受け付け、戻す前にいまの状態の復元点（操作名 `undo-restore`）を作る
- 手順 5（戻した後に自動で保存）は**未実装**。設定 `auto_save_after_restore` は保存されるが、元に戻す処理は commit を作らない（戻した結果は未保存の変更として残る）

**新規ファイルの「元に戻す（作成しない）」**（`core-ops` の `discard_new_file`、Tauri コマンド `discard_new_file`。操作名 `discard-new-file`）:

一度も保存されていない新規ファイル（未追跡）には、戻す先の版が無い。そこで、利用者が明示的に選んだときに限り、そのファイルを**作業フォルダから OS のごみ箱へ移す**。これは安全上の不変条件 6（6.4）の唯一の例外で、完全な削除ではない。次の安全策をすべて満たしたときだけ実行する。

1. **対象は単一の未追跡ファイルだけ**: `git ls-files -z -o --exclude-standard -- :(literal)<パス>` に出るファイル（保存対象外のファイルは対象外。復元点に入らないため）。ディレクトリ・追跡済みのファイル・インデックスに登録済みのファイル・シンボリックリンク・見つからないファイルは拒否する。パスは `normalize_project_path` と `resolve_entry_in_project` で検査し、プロジェクト外（`..`・絶対パス・リンク経由）は `invalid_input` で拒否する。変更のぶつかりが残っているときは `conflict`
2. **復元点を作る**（6.2。操作名 `discard-new-file`）: 実行前に、そのファイルの内容を含む復元点（`refs/hikae/snapshots/...` と `refs/hikae/backup/discard-new-file/...`）を、既存の復元点の作成関数で作る。一時インデックスで作るため、作業フォルダとインデックスは変わらない。そのうえで、**復元点の中のファイルの内容（`git cat-file -p <復元点>:<パス>`）が、いまのファイルとバイト単位で一致すること**を確かめる。確かめられなければ削除しない（`discard_not_backed_up`）。同じ内容の自動保存が既にあって新しい復元点が作られなかったときは、直近の自動保存で確かめる
3. **復元点に入らない大きさのファイルは削除しない**: 大きさが設定「大きいファイルの警告閾値」（`large_file_warn_mb`。自動保存から除外される大きさと同じ）を**超える**ファイルは、復元できないため何も変更せず `discard_file_too_large` で断る。画面は「そのまま残すか、保存するときに『保存対象から外す』を選んでください」と案内する（保存対象から外す操作そのものは、4.1 の大きいファイルの選択で行う）
4. **削除の直前に再確認する**: 復元点の作成と内容の確認のあと、通常のファイルのままで、まだ未追跡であることをもう一度確かめる
5. **ごみ箱へ移す**: `core-ops` の `Trasher`（trait）が行う。`app` は `trash` crate（`=5.2.9` に固定）を使う実装（`OsTrash`）を渡し、テストでは一時フォルダへ移す実装に差し替える。ごみ箱へ移せなかったとき（ごみ箱が使えない環境を含む）は、ファイルを削除せず `trash_failed` を返す。他のアプリが開いている（Windows の共有違反）ときは `file_in_use`
6. **直列キューとジャーナル**: 状態を変更する操作として、同一プロジェクトの直列キュー（`run_op`）で実行する。ジャーナルには、操作名・結果・対象の**パスだけ**を残す（ファイルの内容は記録しない）

確認ダイアログ（D2 と同じく、取り消せる操作なので「元に戻す」は danger ではなく primary）は、5章の 3 要素で次の文言にする。「『{ファイル名}』を作る前の状態に戻します」「このファイルを作る前の状態に戻します。ファイルはごみ箱に移され、履歴の控えからも取り戻せます。」ボタンは「キャンセル」「元に戻す」。

成功後のトースト「『{ファイル名}』をごみ箱に移しました」には「取り消す」を付ける。取り消しは、ごみ箱からの復元ではなく、**復元点からの復元**（既存の `undo_restore`。戻す前にいまの状態の復元点を作る）で行う。取り消し用の ref は `discard_new_file` の戻り値 `undo_token`。取り消すと、ファイルは復元点の内容で作業フォルダに戻る（登録済みの新規ファイルとして戻るため、再び「作成しない」の対象にはならない）。ごみ箱に残った同じ内容のファイルは、そのまま残る。

### 4.3 最新を取り込む

1. 未保存の変更がある場合: `snapshot()` 後、「取り込む前に自動で保存」（初期値オン）なら 4.1 の手順で commit。オフなら確認ダイアログ（実装は下記の補足を参照）
2. `git fetch --prune origin`
3. `git rev-list --left-right --count HEAD...@{u}` でアップロード待ち／取り込み待ちを算出
4. 取り込み待ちのみ: `git merge --ff-only @{u}`
5. 双方に差がある: `git update-ref refs/<app>/backup/pre-merge/<時刻> <HEAD の OID>`（`rev-parse HEAD` で解決した完全な OID を渡す。`update-ref` は値に OID のみ受け付ける）の後、`git merge --no-edit @{u}`
6. 競合なし → 完了。競合あり → 4.4
7. 自動アップロードがオンなら 4.5
8. 追加処理: 取り込みで「除外設定により相手側で追跡を外されたファイル」が削除される場合、マージ前の内容を作業フォルダに書き戻す（4.8 の注意点への対策）

実装の補足（`core-ops` の `pull`）:

- 前提: 未解決の競合が残っていれば取り込まずに `conflict` を返す。upstream が未設定なら何もせず「upstream なし」として終える
- 順序: `fetch --prune` は作業フォルダ・インデックスを変えないため、復元点より**先**に実行する。その結果で、取り込む内容（取り込み待ち）も自動保存する内容（未保存の変更）も無いと分かれば、**復元点を作らず**「最新です」（`UpToDate`）として終える。1 回の取り込みで作る復元点は最大 1 組（操作名 `pull`）で、双方に差があるときは手順 5 の `pre-merge` が加わる
- サイズ検査: 未保存の変更があるときは、取り込み前の自動保存にも 4.1 手順 1 と同じ検査を行う。警告（閾値超）または保存不可のファイルが 1 件でもあれば、**何も変更せず**（復元点も作らず）取り込みを見送り、該当ファイルを構造化した結果（`PullResult.size_check`。アップロード中の取り込みなら `PushResult.size_check`）で返す。取り込み側には「そのまま」の承諾は無く、画面で保存の手順（外す／承諾）を済ませてから取り込みをやり直す。自動実行のときは `NeedsAttention`（理由 `large-files`）で画面に知らせる
- 自動保存のメモ: 「取り込み前の自動保存」（呼び出し側が渡す文言）に、4.1 と同じ `Hikae-PC` トレーラーを付ける。自動保存の commit が増えるため、自動保存後にアップロード待ちを数え直す
- 「取り込む前に自動で保存」の設定（`save_before_pull`）をオフ（「確認する」）にした場合の動作は、起動元で分かれる
  - **自動**の取り込み（スケジューラ）: 未保存の変更があれば取り込まずに `NeedsAttention`（理由 `unsaved-changes`）で知らせる
  - **手動**の取り込み: `pull(id, save_confirmed)`。設定が「確認する」で `save_confirmed` が偽のとき、`Ops::pull_with_policy(.., UnsavedPolicy::Confirm)` で実行する。`fetch --prune` の後、**取り込む内容（取り込み待ち）と未保存の変更の両方がある**ときだけ、何も変更せず（復元点も作らず、サイズ検査より前に）`PullOutcome::NeedsSaveConfirmation { unsaved_count }` を返す。画面は結果 `needs-save-confirmation` と `PullResult.unsaved_count` で E06 の確認ダイアログを出す。取り込む内容が無ければ、未保存の変更には触れず `UpToDate` で終える（保存は取り込みの前処理のため）。利用者が「保存して取り込む」を選ぶと `save_confirmed = true` で呼び直し、従来どおり（復元点 → 自動保存 → 取り込み、サイズ検査を含む）に実行する。設定がオン、または `save_confirmed` が真のときは `UnsavedPolicy::SaveFirst`（従来の動作）
  - アップロード中の取り込み（`upload`）は常に `SaveFirst`。確認は取り込みの操作にだけ付く
- 手順 8 の実際の範囲（`restore_files_untracked_by_remote`）: 取り込み前の HEAD にあり取り込み後の HEAD に無いパス（`diff --name-only -z --no-renames --diff-filter=D`）のうち、(a) 取り込み後の .gitignore で保存対象外（`git check-ignore -q`）になっていて、(b) 作業フォルダに実体（リンクを含む）が無いものだけを、`git restore --source <取り込み前の HEAD> --worktree -- :(literal)<パス>` で 1 ファイルずつ書き戻す。相手が実際に削除したファイル（保存対象外になっていないもの）は書き戻さない。既にファイルがあるパスは上書きしない。インデックスは変更しない（`rm` は使わない）。個々の失敗は取り込みの失敗にしない（取り込み前の内容は復元点に残る）。早送り・マージ成功の直後に行い、競合で止まった取り込みでは 4.4 の解消後に行う

### 4.4 変更のぶつかり解消

1. 対象一覧: `git status --porcelain=v2 -z` の `u` 行（両方変更／片方削除を区別）。`-z` 形式ではエントリが NUL 区切りで、パスは空白区切りフィールドの末尾に置かれる
2. 「この PC の版」: `git checkout --ours -- <path>`、「クラウドの版」: `git checkout --theirs -- <path>`
3. 「使わなかった版を別名で残す」: `git show :3:<path>`（または `:2:`）の内容を `<名前> (クラウドの版 MM-DD).<拡張子>` として書き出す
4. 片方が削除している場合: 「残す」／「削除を受け入れる」の2択（`git add` または `git rm --cached`。作業フォルダの実体はアプリが削除する。`GitRunner` は `--cached` なしの `rm` を許可しない）
5. 行単位編集（テキストのみ、Phase 2）: `:1:`（共通の元）、`:2:`、`:3:` を取得し、アプリ内の3ペインで組み立てて書き込む
6. 全件解消後: `git add <paths>` → `git commit --no-edit`（メモは「2台の変更をまとめました」に置換）
7. 「あとで」: `git merge --abort`。復元点 `pre-merge` が残っているので状態は完全に戻る
8. 解消後の書き戻し: 手順 6 の保存の**後**に、4.3 手順 8 と同じ書き戻しを行う。競合で止まった取り込みでも、相手が追跡を外したファイルが取り込みで消えていれば、競合前の HEAD（競合中も HEAD は動かない）の内容を作業フォルダへ戻す

実装の補足（`core-ops` の `resolve` / `conflicts` / `abort_merge`）:

- 競合情報（`ConflictFile`）には、競合の種類（両方変更・両方追加・この PC で削除・クラウドで削除・両方削除）に加えて、各側でそのファイルを最後に変更した保存の日時（Unix 秒）と、その保存を作った PC の名前（`Hikae-PC` トレーラー）を含める。取得は `git log --max-count=1 --format=%ct%x1f%B <HEAD または MERGE_HEAD> -- <パス>` で、解析できなければ `None`（画面は日時・PC 名を隠す）
- 解消は競合している**全ファイル**分の選択を一度に受け取る（不足があれば `unexpected` で拒否）。実行前に復元点（操作名 `resolve`）を作る
- 手順 3 の別名は、元のファイルと同じフォルダに `<名前> (<ラベル> MM-DD).<拡張子>`（ラベルは「この PC の版」「クラウドの版」）で書き出す。同名があれば `MM-DD 2` のように連番を付け、既存のファイルは上書きしない
- 保存のメモは「2台の変更をまとめました」。「あとで」は `abort_merge`（復元点 `abort-merge` を作ってから `merge --abort`）
- 解消の完了後は、スケジューラが取り込みとアップロードを予定する

### 4.5 アップロード

1. `git push origin HEAD`（`--force` 系は内部でも使わない）
2. 拒否（相手側が先に進んでいる）: 4.3 を実行してから1回だけ再試行。再度失敗したらエラー表示
3. upstream 未設定時のみ `git push -u origin HEAD`。保存が 1 つも無いときは何もしない（`push` が失敗するため）。保存先（remote）は設定済みで一度もアップロードしていない（upstream なし）ときの「アップロード待ち」は、作った保存の総数とする（`project_status`）

### 4.6 リポジトリの作成・取得

| 操作 | GitHub API | Git |
| --- | --- | --- |
| 保存先の一覧 | `GET /user`、`GET /user/orgs` | — |
| 新規作成（個人） | `POST /user/repos`（`private: true` 初期値） | `git init -b main` → `git remote add origin` → 初回保存 → `git push -u` |
| 新規作成（Org） | `POST /orgs/{org}/repos` | 同上 |
| 既存フォルダを登録 | 上記いずれかで空リポジトリを作成 | 既存の `.git` があれば再利用し remote のみ追加 |
| GitHub から取得 | `GET /user/repos?affiliation=owner,organization_member` | `git clone` |

Org に作成権限がない場合は API が 403 を返すため、作成ダイアログで保存先を選んだ時点で `GET /orgs/{org}/memberships/{login}` を確認し、作れない保存先は灰色表示にします。

実装状況（2026-10-08）:

- 保存先の一覧は実装済み。個人と `GET /user/orgs` の Organization を並べ、各 Organization について memberships（承認待ちの検出）と `GET /orgs/{org}` の `members_can_create_repositories` を確認し、作れない理由（参加の承認待ち・メンバーによる作成が不許可・情報を確認できない）を返す
- GitHub から取得（`git clone`）は実装済み。一覧は `GET /user/repos?affiliation=owner,organization_member` をページ送りで取得し、件数が多いときは `truncated` で知らせる。取得先 URL は常に `https://github.com/<owner>/<name>.git` に固定し（owner と name は英数字・`-`・`_`・`.` のみ）、任意の URL は受け付けない。取得先のフォルダは存在しないか空である必要があり、空でなければ中身に触れず拒否する。新しいフォルダを作るだけなので復元点は作らない。git の待ち時間は 30 分に延ばし、完了後に署名と `core.autocrlf=false` / `core.precomposeUnicode=true` をリポジトリ単位で設定して登録し、操作ジャーナルへ `clone` を記録する
- 既存フォルダの登録・新規作成（`add_project`）は、`git init -b main`（既存の `.git` があっても同じ手順を通す）とリポジトリ単位の設定でローカルに登録したあと、画面が保存先を選んでいて（`remote` を渡したとき）ログイン済みなら、続けて GitHub 上のリポジトリを作り、保存先として接続する。既存の `.git` がすでに `origin` を持っているときは、それを保存先として登録し、新しくは作らない。保存先の無いプロジェクトは、取り込み・アップロードの自動実行の対象にならない
- **リポジトリの作成と接続**（`core-github` の `GithubApi::create_repository`、`app/src/remote.rs` の `connect_flow`。新規の追加と、あとから接続する `connect_remote` で共通）:
  1. 公開（`private: false`）は、画面の警告に同意した明示のフラグ（`public_confirmed`）が無ければ、何も作らずに拒否する（`remote_public_not_confirmed`）。画面の既定は非公開
  2. 保存先が個人（ログイン名と同じ）なら `POST /user/repos`、それ以外は Organization として `POST /orgs/{org}/repos`。送る前に所有者名（英数字と `-`、39 文字以内）とリポジトリ名（英数字と `-`・`_`・`.`、100 文字以内。`.` / `..`、`.git` / `.wiki` で終わる名前は予約名として拒否）を検証する。名前を指定しないときは、プロジェクト名から ASCII の英数字だけを残して作り、日本語の名前などで何も残らなければ `hikae-<ID の先頭 8 文字>` にする
  3. 失敗の分類: 401 は E01、403 と Organization が見えない 404 は E02（`github_forbidden`）、レート制限、通信できないは E03（`network_unavailable`）、5xx は E04、同名がすでにある 422 は専用の `remote_name_taken`（GitHub にもローカルにも何も変わらない）。応答の本文・URL・トークンはエラーに含めない
  - **作成の前の検査**（`core-ops` の `Ops::preflight_connect`。読み取りのみで、作業フォルダ・インデックス・`.git/config` に書き込まない）: GitHub に何かを作る前に、(a) `origin` が別の場所を指していないか（指していれば `remote_conflict`。接続先と同じ場所なら前回の途中で止まった接続の続きとして、GitHub には作らずに進める）、(b) `.git/config` に書き込めるか（`remote_not_writable`）、(c) フォルダが存在しリポジトリか（`project_folder_missing`。E11 と同じ判定）、(d) 保存が 1 つも無く初回の保存を作る場合に、保存不可（100MB 超）や確認が必要（警告閾値超）のファイルが対象に含まれないか、を確かめる。(d) に該当するときは、GitHub に何も作らず、`RemoteConnectResult.size_check` に内容を入れ、`connected=false` で返す。画面は既存の大きいファイルの 2 択（`SizeCheckDialog`）を出し、選択を `save_with_size_choice`（メモは「最初の保存」）で保存に反映してから、`connect_remote` で接続をやり直す。キャンセルすればローカルだけの登録が残る。名前と所有者の規則の検証（`remote_name_invalid`、`remote_owner_invalid`）も、通信の前に行う
  - **同名の空の保存先への接続の提案**: 作成が 422（同名）のとき、`GET /repos/{owner}/{name}` と `GET /repos/{owner}/{name}/commits?per_page=1` で既存の保存先を調べる（`GithubApi::check_adoptable_repository`）。(a) 自分に書き込み権限があり（`permissions`。アーカイブ済み・無効化は不可）、(b) 保存が 1 つも無い（409 `Git Repository is empty`、または 200 で空の配列かつ `size` が 0）ときだけ、新規作成せずに `RemoteConnectResult.existing_empty_repository`（`owner/name`）で返す（何も作らず、ローカルも変更しない）。画面は「すでに同じ名前の空の保存先があります。ここに接続しますか」と確認し（接続する／別の名前にする／キャンセル）、承認されたら `RemoteRequest.adopt_existing=true` で呼び直す。バックエンドは承認後にも空で書き込めることを再確認し、満たさなければ接続しない。空でない保存先、読み取り専用の保存先、見えない保存先は決して自動では接続せず、`remote_name_taken` のままにする（他人・他のプロジェクトのデータを上書きしない。アップロードは force しない）。非公開を求めたのに既存の保存先が公開のときも、ファイルが公開されてしまうため接続しない
  4. 作成（または承認された既存の空の保存先への接続）ができたら、`run_op`（直列キュー、操作名 `connect-remote`）の中で `origin` を `https://github.com/<owner>/<name>.git`（認証情報を含めない。認証は credential helper）に設定し、プロジェクトの保存先 URL と所有者を記録する。`add_project` では、まだ 1 つも保存が無く変更があるときだけ、通常の保存（復元点とサイズ検査を通る。メモは「最初の保存」）を作る。大きいファイルがあれば保存を見送り、結果の `size_check` で知らせる
  5. 続けて通常のアップロード（`run_op`、操作名 `push`。upstream が無いので `push -u origin HEAD`）を実行する。保存が 1 つも無いときは何もしない
  - 保存先を GitHub に用意したあとの (2)(3) の失敗は `remote_orphaned`（params: `name` = `owner/name`）で返す。GitHub 上に空の保存先が残っていること、ファイルはこの PC に安全に残っていることを伝える。もう一度「接続する」を押すと、同名の空の保存先として上記の提案が出るため、そのまま接続できる（不要なら GitHub 上で利用者が削除する。アプリは `delete_repo` 権限を使わず、保存先を削除しない）
  - 途中で失敗した場合: リポジトリの作成に失敗したときは、ローカルの登録だけが残り（保存先なし）、`add_project` は `AddProjectResult.remote.error` に E02 / E03 などの 3 要素のエラーを入れて成功で返す。`connect_remote` は作成前の失敗をエラーで返す。作成後のアップロードの失敗は、保存先は接続済みのまま `error` に入れて返し、ヘッダーは「アップロード待ち」になる（スケジューラまたは手動のアップロードが `push -u` をやり直す）
  - 未ログインのときは、画面がローカルだけで登録し（保存先と公開範囲の入力を求めない）、ログイン後に `connect_remote` で接続できる。実機で保存先なしのまま作ったプロジェクトも同じ。すでに保存先がある場合は `remote_already_connected`
  - ジャーナルの対象は `<owner>/<name>` だけで、トークンも認証情報付きの URL も残さない（不変条件 9）
- 画面（`ConnectRemoteDialog`、`RemoteTargetFields`）: 保存先（OwnerPicker）、公開範囲（初期は非公開。公開を選ぶと警告文と確認のチェックが必要）、任意の GitHub 上の名前（同名の衝突のときに指定し直せる）。保存先に接続していないプロジェクトは、一覧のカードとプロジェクト画面のヘッダーに「GitHub に接続していません」と「接続する」を出す

### 4.7 ファイルの追加・外部で開く

- D&D: Rust 側でプロジェクト内へコピー（移動ではない）。同名がある場合は「置き換える／両方残す（連番）」を選択。コピー直後にサイズ検査を行う
  - 実装: 置き換える選択は設けず、同名があれば常に `名前 (2).ext` のように連番を付けた別名にして、既存のファイルを上書きしない（`create_new` で作成と存在確認を同時に行う）。追加先はプロジェクト直下のみで、フォルダの選択は未実装。コピー前に復元点（操作名 `add-files`）を作り、保存（commit）はしない
  - サイズ検査はコピー前に元のファイルで行う。100MB を**超える**ものはコピーせず理由つきで断り（E07）、50MB を**超える**ものはコピーして `large` で知らせる（E08）。この 50MB は定数で、設定 `large_file_warn_mb` には従わない。フォルダなどファイルでないもの、読めないものも理由つきで断る
- 既定のアプリで開く: Tauri の opener プラグイン。実装は Rust 側（`OpenerExt::open_path`）からのみ呼び、画面側（JS）には opener の権限を与えない（`capabilities/default.json` は `core:default` と `dialog:default` のみ）
  - 開く前に Rust 側でパスを検証する（`resolve_in_project`）。(1) 字句検査: 空・NUL を含むもの、先頭が `/` または `\`（絶対パス・UNC）、ドライブ指定（`C:`）、`/` と `\` のどちらで区切っても `..` を含むもの、Windows では `:` を含むもの（代替データストリーム）を拒否。(2) 実体検査: プロジェクトのルートと結合後のパスをそれぞれ `canonicalize` し、後者がルートの配下で、かつルート自身でないことを確認（シンボリックリンクやジャンクションで外へ出るものを拒否）
  - 拒否・失敗はエラーコード `outside_project`、`file_not_found`、`file_unreadable`（5.1）で返す
- フォルダで表示: Rust 側の opener の `reveal_item_in_dir`（Windows は `explorer /select,` 相当、macOS は `open -R` 相当）を、`reveal_project_file` コマンドから呼ぶ。「既定のアプリで開く」と同じ検証（`resolve_in_project`）を通したパスだけを渡し、画面（JS）には opener の権限を与えない（`capabilities/default.json` は変更していない）。失敗は `open_failed`
- パスをコピー: 画面側でクリップボードへ書き込むだけで、バックエンドは呼ばない。プロジェクトの場所の区切り文字に合わせて結ぶ（`components/file-actions.ts`）
- 「開く」メニューの項目は、既定のアプリ・フォルダで表示・パスをコピーの 3 つ
- **VS Code で開くは実装しない**: 外部コマンド（またはその URL スキーム）の実行になり、検証の対象と権限が広がるため。メニューにも出さない（設定 `open_action` の `vs-code` はスキーマにだけ残り、画面には出さない）。要望が出た場合は、実行する対象を固定した上で改めて設計する
- 過去の版を開く: `git show <時点>:<path>` を一時フォルダに書き出し、読み取り専用属性を付けて開く
  - 実装: 時点を完全な OID に解決し、`ls-tree` で通常のファイルとして存在することを確認してから、`git cat-file -p <OID>:<パス>` で内容を読む（許可リストは変更していない）。パスは `..`・絶対パス・ドライブ指定・`.git` 配下・先頭が `:` のものを拒否する。コミットは先頭が `-` のものや空白・制御文字を含むものを拒否する
  - 書き出し先は `<temp>/hikae-preview/<プロジェクト ID>/<12 桁のコミット>/<相対パス>`（`<temp>` は OS の一時フォルダ）。プロジェクト ID は英数字・`-`・`_` のみ 128 文字以内を許す。作業フォルダにもリポジトリにも書かない。書き出したファイルは読み取り専用にする（開いたアプリでの編集が履歴に紛れ込まないように）。同じ内容のファイルが既にあれば書き直さない
  - 古い一時ファイルは起動時に別スレッドで削除する。`<12 桁のコミット>` のフォルダ単位で、配下のファイルの最終更新が **7 日**より前のものを、読み取り専用を解除してから削除し、空になったプロジェクトのフォルダも片付ける。削除に失敗したもの（他のアプリで開いている等）は残す

### 4.8 保存しないファイル（.gitignore）

1. パターンを追加: 拡張子・フォルダ・個別ファイルを GUI で選び、.gitignore に追記して保存
2. `git ls-files -ci --exclude-standard` で「すでに保存対象になっている該当ファイル」を検出
3. 該当があれば次の2択を表示
   1. **今後の変更だけ無視する**: `git update-index --skip-worktree <path>`。クラウドには今の版が残る。設定はこの PC のみ有効なため、アプリ設定に記録し、他の PC で同じプロジェクトを開いたときに再適用を提案する
   2. **保存対象から外す**: `git rm --cached -r <path>` → 保存。PC 上のファイルは残る。過去の保存ポイントには残る
4. 2 を選んだ場合の注意: 他の PC が取り込むと、Git はそのファイルを削除する。4.3 の手順8で書き戻して防ぐ
5. 「過去の履歴からも完全に消す」（パスワード等を誤って保存した場合）は履歴の書き換えが必要なため対象外とし、ヘルプで GitHub のドキュメントへ案内する

## 5. エラー・例外ケースと文言案

### 5.1 実装でのエラーの扱い

**返す型と文言の決まり方**

- Rust のコマンドは失敗を `AppError` で返す。項目は `code`（機械可読なエラーコード）、`params`（文言に差し込む値。ファイル名・件数など表示用の値だけで、トークン・認証情報・git の標準エラー出力は入れない）、`what_happened` / `data_is_safe` / `next_action`（日本語の 3 要素）、`technical_info`（「技術情報を表示」欄用。git の標準エラー出力など）
- 画面は `code` と `params` から、`src/lib/i18n/ja.ts` の `errcode.<code>.what` / `.safe` / `.next` を引く。**3 つがそろい、差し込む値も足りているときは ja.ts の文言を優先する**。コードが未知、文言が無い、値が足りないときは、Rust 側が返した 3 要素をそのまま表示する。このため、どのエラーでも「何が起きたか」「データは無事か」「次の行動」の 3 要素がそろう
- 本節の**すべてのコード**に ja.ts の `errcode.*`（3 要素）がある（`error-view.test.ts` が一覧を検査する）。Rust 側の 3 要素が表示されるのは、コードが未知のとき、または params の値が足りないときだけ。内部エラー系（`task_failed`、`lock_failed`、`database_error` など利用者が対処できないもの）は汎用の文言にしている
- 設計書の E01〜E20 の文言（`error.E01` など）は ja.ts にあるが、バックエンドのエラー（`errcode.*`）の表示には使わない。画面側で直接生成するのは E11 だけ（下の対応表）

**エラーコード**（`app/src/lib.rs` の `AppError` の説明に従う。`OpsError` と認証エラーに 1 対 1 で対応）

- 操作: `conflict`（params: `count`）、`git_failed`、`git_timeout`、`safety_check_failed`、`io_error`、`file_in_use`（params: `file`。特定できたときのみ）、`invalid_input`、`restore_point_not_found`、`unexpected`
- 中断された操作の復旧（`recover_interrupted` が返す。`AppError` の説明の一覧には載っていない）: `no_interrupted_operation`、`not_recoverable`（params: `operation`）
- 新規ファイルの「元に戻す（作成しない）」（4.2）: `discard_not_untracked`（すでに保存の対象になっている、または保存対象外）、`discard_not_a_file`（フォルダ・リンク・見つからない）、`discard_file_too_large`（復元点に入らない大きさ）、`discard_not_backed_up`（復元点にファイルの内容を確認できない）、`trash_failed`（ごみ箱へ移せない）。どれも `params` は `file`（ファイル名だけ。パスは含めない）で、**ファイルは削除していない**（データの安否の文は「ファイルは削除されていません。」）。他のアプリが開いているときは `file_in_use`、プロジェクト外は `invalid_input`、ぶつかりが残っているときは `conflict`
- ファイルを開く: `file_not_found`、`file_unreadable`、`outside_project`
- 認証・GitHub: `not_logged_in`（E01）、`github_forbidden`（E02）、`github_rate_limited`、`network_unavailable`（E03）、`github_unavailable`（E04）、`login_not_configured`、`keychain_error`、`login_not_in_progress`、`login_page_unexpected`、`browser_open_failed`、`github_error`
- 取得（clone）: `clone_invalid_repo`、`clone_invalid_destination`、`destination_not_empty`、`destination_not_a_folder`、`destination_unreadable`、`remote_not_found`（E16）、`clone_failed`、`clone_timeout`、`clone_register_failed`
- 保存先の作成・接続: `remote_name_taken`（同名のリポジトリがすでにある。空で書き込めるものは、エラーではなく接続の提案になる）、`remote_name_invalid`、`remote_owner_invalid`、`remote_public_not_confirmed`、`remote_already_connected`、`project_folder_missing`、`remote_conflict`（`origin` がすでに別の場所を指している）、`remote_not_writable`（`.git/config` に書き込めない）、`remote_orphaned`（GitHub 上に空の保存先ができたが、プロジェクトに接続できなかった。params: `name`）。権限不足は `github_forbidden`（E02）、通信できないは `network_unavailable`（E03）
- プロジェクト: `project_not_found`、`project_already_registered`、`folder_already_registered`、`project_list_failed`、`project_register_failed`、`project_remove_failed`、`relocate_not_a_project`、`relocate_different_project`、`relocate_cannot_verify`、`relocate_failed`
- 内部: `database_error`、`task_failed`、`lock_failed`、`settings_io_failed`、`invalid_settings`、`status_failed`、`history_failed`、`diff_failed`、`change_list_failed`、`conflict_list_failed`、`preview_failed`、`open_failed`

**大きいファイル（E07 / E08）はエラーではない**: 保存・取り込み・アップロードの結果の一部として、該当ファイルのパスとサイズ（`SizeCheckResult`: `blocked` と `warned`）を返す。何も変更していないため、エラーコードは持たない。画面は専用のダイアログで 2 択を出す（4.1、4.3）。

**E12（ファイル使用中）の判定**: 次のどちらかに当てはまるとき `file_in_use` にする（`core-ops` の `file_in_use`。共有違反は `OpsError::FileInUse` に分類され、`Git` や `Io` としては返らない）。

- git の標準エラー出力（大文字小文字を区別しない）に、OS が共有違反を直接伝える文言（`being used by another process`、`sharing violation`、`device or resource busy`）がある。または、ファイルの削除・作成の失敗を示す git の文言（`unable to unlink`、`unlink of file`、`could not unlink`、`cannot unlink`、`unable to create file`、`unable to write file`）と、その理由（`permission denied`、`invalid argument`、`busy`、`failed` のいずれか）がそろっている（`unlink of file` は文言と理由を兼ねるため、それだけで該当する）。Windows の git は共有違反を `Permission denied` や `Invalid argument` で報告するため、失敗の文言と理由の両方がそろった場合に限って採用する
- アプリ自身のファイル操作の `std::io::Error` が、Windows の OS エラー 32（共有違反）または 33（ロック違反）
- 判定は英語の文言に依存する。`GitRunner` は git の実行時に環境変数を引き継がず、`LC_ALL=C` を設定して出力を英語に固定する。特定できたファイルの名前は `params.file` に入れる（パスは含めない）

**自動再試行の間隔**（`core-watch` の `retry_delay_secs`。失敗が続くごとに倍にし、上限で止める）: オフライン（E03）は 30 秒から上限 10 分（30 秒、1 分、2 分、4 分、8 分、10 分）。認証失敗（E01）は 5 分から上限 60 分。それ以外（GitHub 側の障害を含む）は 60 秒から上限 30 分。変更のぶつかりが残っている間は 15 分ごとに状態を確かめる。

## 6. 安全設計・内部バックアップ戦略

安全性は「危険なコマンドを実行層で拒否する」「状態変更の前に必ず復元点を作る」「中断を検出して戻せる」の3層で担保します。UI で隠すだけでは、将来の機能追加やバグで破壊的操作が混入するため、実行層で強制します。

### 6.1 第1層: コマンドの許可リスト

Rust 側の `GitRunner` は、引数を含めて許可リストに一致する呼び出しのみ実行します。以下は呼び出し側のコードに書かれていても実行時に拒否します。

- `push` の `--force` / `--force-with-lease` / `+refspec`、`--delete`、`--mirror`
- `reset --hard`、`clean`、`branch -D`、`checkout -f`、`restore` を `--source` なしで worktree に適用する呼び出し（未保存変更の破棄になるため）
- `rebase`、`filter-branch`、`commit --amend`、`gc --prune=now`、`reflog expire`

実装は上の禁止リストではなく**許可リスト方式**（default deny）です。サブコマンドごとに許可するフラグを列挙し、列挙にないフラグはすべて拒否します。git は長いオプションの省略形（`--forc` など）を受け付けるため、禁止リスト方式では回避されるからです。`-c` で渡せる設定キーも許可リストで制限し（`alias.*`、`core.sshCommand` などは拒否）、`fetch --prune` は remote-tracking ref の整理のみなので許可します。
- `update-ref` は作成・更新・削除のすべてを自アプリの名前空間（`refs/<app>/`）以外では拒否する。値は完全な OID のみ受け付け、削除を意味する全ゼロ OID も拒否する（`-d` を複数回指定して検査を回避する手口と、全ゼロ OID による削除を塞ぐため）

実装の補足（`core-git`）:

- 実装では `<app>` は `hikae`（`refs/hikae/`）。名前空間の定数は `refs/hikae/snapshots/` と `refs/hikae/backup/`
- 許可リストに無いサブコマンドは「unknown subcommand」として実行前に拒否する。`reset`、`clean`、`rebase`、`filter-branch`、`gc`、`reflog`、`stash`、`tag`、`pull`、`cherry-pick`、`revert`、`worktree`、`submodule` は明示的に拒否する。`diff-tree` のように git の標準のコマンドでも、許可リストに無ければ実行時に失敗する（13.3）
- `-c` で渡せる設定キーは、`core.hooksPath`、`core.autocrlf`、`core.precomposeUnicode`、`core.quotepath`、`core.longpaths`、`credential.helper`、`user.name`、`user.email`、`commit.gpgsign`、`init.defaultBranch`、`protocol.version` のみ。子プロセスの環境変数は引き継がず（`PATH`、`SystemRoot`、`SYSTEMDRIVE`、`TEMP`、`TMP`、`TMPDIR` だけを渡す）、`GIT_CONFIG_GLOBAL` を null デバイス、`GIT_CONFIG_NOSYSTEM=1`、`GIT_TERMINAL_PROMPT=0`、`LC_ALL=C` に固定する。読み取り専用のコマンドには `GIT_OPTIONAL_LOCKS=0` を付ける。追加で渡せる環境変数は `GIT_INDEX_FILE` と作者・コミッターの 6 個だけ
- 待ち時間の上限は 60 秒（取得は 30 分）。超えるとプロセスを止めて `git_timeout` にする

### 6.2 第2層: 復元点（隠し ref）

実装では `<app>` は `hikae` です（`refs/hikae/`）。

| 名前空間 | 作成タイミング | 指す先 | 保持期間 |
| --- | --- | --- | --- |
| `refs/hikae/snapshots/<ブランチ>/<時刻>` | 状態を変える操作の直前（下記）と、ファイル監視による自動保存（「自動保存の作り方（ファイル監視）」） | 作業フォルダ全体（未保存変更を含む）の commit | 7日未満は全件、30日までは1時間に1件、保持期間（設定 7〜730 日。選択肢は 30 / 90 / 365 日とカスタム。初期値 90 日）までは1日に1件。下記の規則 |
| `refs/hikae/backup/<操作名>/<時刻>` | 状態を変える操作の直前（下記）と、双方に差がある取り込みの merge の直前（`pre-merge`） | その時点の HEAD | 90日 |

復元点を作る操作（`<操作名>`）は、保存（`save`）、取り込み（`pull`）、元に戻す（`restore`）、1 ファイルを戻す（`restore-file`）、元に戻すの取り消し（`undo-restore`）、ぶつかり解消（`resolve`）、ぶつかり解消の中止（`abort-merge`）、ファイルの追加（`add-files`）、新規ファイルの「元に戻す（作成しない）」（`discard-new-file`。4.2）です。1 回の操作で、スナップショットと `HEAD` を指す backup ref を 1 組作ります。時刻は UTC の `YYYYMMDDTHHMMSSZ` で、同じ名前が既にあれば `-1`、`-2` と連番を付けます。`HEAD` がまだ無い（最初の保存の前）ときは backup ref を作りません。

**スナップショットの作り方**（作業フォルダとインデックスを一切変更しない）:

1. 一時インデックス `GIT_INDEX_FILE=<リポジトリの .git>/hikae/tmp/index-<ランダムな ID>` を作る。`HEAD` があれば `git read-tree <HEAD の OID>`、無ければ `git read-tree --empty`。処理の終了時に一時インデックスを削除する
2. 同じ一時インデックスに `git add -A` → `git write-tree`
3. ツリーが、直前のスナップショットのツリー、または `HEAD` のツリーと同一なら、スナップショットは作らない（重複を作らない）
4. `git commit-tree <tree> -m "auto: <時刻>" -p <HEAD の OID>`（作者・コミッターは下記の署名）→ `git update-ref refs/hikae/snapshots/<ブランチ>/<時刻> <OID>`

**自動保存の作り方（ファイル監視）**（Phase 1 に前倒しして実装。判断は `core-watch`、作成は `core-ops` の `auto_snapshot` と `core-safety` の `create_snapshot_excluding`、実行は `app` の `auto_snapshot.rs`）:

- 契機: 登録済みのプロジェクトのフォルダ（フォルダが見つかるもの。リモートの有無は問わない）を `notify` + `notify-debouncer-full` で監視し、変更を検知するたびに「最後の変更の時刻」を更新する（8.2、9.2）。最後の変更から `auto_snapshot_delay_secs`（初期値 120 秒。範囲 10〜3600 秒）の間、新しい変更が無かった（静止した）ときに 1 回作る。変更が続く間は後ろへずれる
- 設定: `auto_snapshot_enabled`（初期値オン）がオフなら作らず、オフの間の変更は覚えない。オンに戻しても、オフの間の変更だけで作ることはしない
- アプリの起動時: 起動直後の静止後に各プロジェクトで 1 回試す（アプリを閉じている間に変わった分を拾う）。変更が無ければ何も作らない
- 作り方: 上の「スナップショットの作り方」と同じ（一時インデックス。作業フォルダとインデックスは変更しない）。作る前に、`git status` で未保存の変更が無ければ一時インデックスを作らずに終える。直前のスナップショットまたは `HEAD` と内容が同じなら作らない
- 大きいファイル: 保存前のサイズ検査（4.1 手順 1）の対象になるファイル（警告・保存不可のどちらも）は、自動保存に含めない。追跡済みのファイルは `HEAD` の内容のまま、未追跡のファイルは含めない（`git add -A -- . ':(exclude,literal)<パス>'` を一時インデックスに対してだけ実行する）。含めなかった件数はジャーナルの結果（`created-without-large-files:<件数>`）に残す。利用者が保存するときは、通常のサイズ検査と選択（4.1）を通る
- 作らない場合: ぶつかりの解消中（ぶつかりのマーカーが入った途中の状態を残さないため。1 分後にもう一度判断する）、ブランチ上にいない（detached HEAD）とき
- 失敗: ステージングに失敗したとき（読めないファイルなど）は、欠けたスナップショットを作らずエラーにする。失敗は 60 秒から上限 30 分まで待ち時間を倍にして再試行する
- 実行: 同一プロジェクトへの状態変更と同じ直列キュー（`run_exclusive`）の内側で実行する。保存・取り込みなどが実行中なら、その完了を待ってから、完了後の作業フォルダの内容で判断する（保存の直後は内容が `HEAD` と同じなので作らない）。`run_op` は使わない: `run_op` は開始時に「実行中」の行を作るため、実行中にアプリが終了すると次の起動で「中断された操作」（E15）として案内してしまう。自動保存は作業フォルダを変更しないので、完了してから結果を 1 行だけ記録する
- 記録: ジャーナル（6.3）に操作名 `auto-snapshot`、`triggered_by = auto` で、作ったときだけ記録する（変更なし・同じ内容・見送りは記録しない）。失敗は種類名だけを記録する。署名は上の「署名」と同じ（ログイン済みなら実ユーザー）
- 表示: 履歴では `refs/hikae/snapshots/` の commit が「自動保存」（`kind = Auto`）として並ぶ。間引き（下記）の対象になる。プロジェクトの画面の左ペイン上部に、「ファイルを変更して 2 分操作しないと、自動で控えを残します。」と「最後の自動保存: 3 分前」（ジャーナルの最後の成功時刻。`project_status` の `last_auto_snapshot_at`）を出す。自動保存がオフのときは、その旨と設定（自動保存タブ）へのリンクを出す

**署名**: スナップショットの作者は、ログイン済みなら GitHub のユーザー名と noreply アドレス（`<id>+<login>@users.noreply.github.com`）。未ログイン、またはユーザー情報を確認できないときは、固定の `Hikae`（メールアドレスは `hikae@localhost`）。名前やメールアドレスが空、または制御文字を含むときも固定の署名にする（`-c user.name=` に不正な値を渡さないため）。

これらの ref は `refs/heads/` の外にあるため、`git push origin HEAD` では送信されず、GitHub 上の履歴にも出ません。整理（間引き）は自アプリの ref の削除のみで行い、実際のデータ削除は Git の通常の `gc`（既定の猶予期間つき）に任せます。アプリ自身は `gc` を実行しません（許可リストで拒否）。

**間引きの規則**（`core-safety` の `plan_thinning`。時刻を引数で受け取る純関数で、実時間に依存しない）:

- 対象はスナップショットと backup の ref だけ。名前空間の外の ref、ブランチ名・操作名が空のもの、空白・制御文字・`..` を含むもの、時刻を読めないものは削除対象にしない
- スナップショットは、ブランチごとに新しい順に見る。経過日数が 7 日**未満**のものは全件残す。7 日以上 30 日（保持期間が 30 日なら 30 日）までは **UTC の 1 時間ごとの枠**に 1 件だけ、それ以降は保持期間までは **UTC の 1 日ごとの枠**に 1 件だけ残し、枠が埋まっていれば削除する。同じ枠では新しいものを残す。保持期間を過ぎたものは削除する
- backup は、操作名ごとに、90 日を過ぎたものを削除する
- 次のものは期間にかかわらず残し、枠も先に使う: 各グループ（ブランチまたは操作名）で最も新しい 1 件、利用者の手動の操作に紐づく復元点（ジャーナルの `triggered_by` が `manual` の行が指す ref。6.3）、未来の時刻のもの（時計のずれ）。保護対象の一覧を読めないときは、間引き自体を見送る
- 実行は、起動直後と 24 時間ごと（スケジューラの保守作業）。同一プロジェクトへの状態変更と同じ直列キューを通し、フォルダが見つからないプロジェクトは間引きを見送る。削除は `update-ref -d` だけで、削除した ref はジャーナルの参照からも外す
- 保持期間は設定 `snapshot_retention_days`（プロジェクト別に上書き可）。backup の 90 日は固定

### 6.3 第3層: 操作ジャーナル

**保存先と変更の理由**: 当初案の `.git/<app>/journal.json` から変更し、アプリ内の SQLite（`core-store` の `journal` テーブル。マイグレーション v2 で作成、v5 で完了時刻を空にできる形へ変更）に記録します。理由は、プロジェクト・開始時刻での検索（索引 `idx_journal_project_started`、`idx_journal_outcome`）と、保持期間による整理を SQL で簡単に行えるためです。リポジトリの中にアプリ独自のファイルを置かずに済む利点もあります。復元点そのもの（ref）はリポジトリ側にあり、ジャーナルの行を消しても復元点は消えません。

**項目**:

| 列 | 内容 |
| --- | --- |
| `id` | 連番 |
| `project_id` | プロジェクト。外部キーは張らず、プロジェクトの登録を外しても記録は残す |
| `operation` | 操作名（`save`、`pull`、`push`、`resolve`、`restore`、`restore-file`、`undo-restore`、`abort-merge`、`add-files`、`discard-new-file`、`recover`、`clone`、`connect-remote`、`auto-snapshot`） |
| `triggered_by` | `manual`（利用者の操作）または `auto`（スケジューラ） |
| `started_at` / `finished_at` | RFC3339。実行中は `finished_at` が空 |
| `outcome` | `running`（実行中）、`success`、`failure`、`interrupted`（中断） |
| `detail` | 結果の要約（`merged`、`up-to-date` など）または失敗の種類 |
| `snapshot_ref` / `backup_ref` | その操作が新しく作った復元点の ref（操作の前後で `refs/hikae/` の一覧を比べて特定する） |
| `target` | 対象（元に戻す先のコミットなど） |

**記録の流れ**（`app` の `run_op`。直列キューの内側で実行する）:

- 操作の本体を実行する**前**に `outcome = running` の行を作り、完了したら `success` または `failure` に更新する。更新は「実行中」の行にだけ効く
- 失敗の `detail` には種類名（`git`、`git-timeout`、`safety`、`io`、`file-in-use`、`conflict`、`invalid-input`、`restore-point-not-found`、`unexpected`）だけを入れ、エラー本文（git の標準エラー出力など）は入れない。記録する文字列は、トークンらしい語・`Authorization` / `Bearer` に続く語・`token=` / `password=` の値・URL のユーザー情報を伏せ、200 文字で切る（不変条件 9）
- スケジューラの自動実行で何も起きなかった操作（最新だった、upstream なし、アップロードするものなし）と、オフラインによる自動実行の失敗は、行を削除して記録に残さない
- 記録に失敗しても操作の成否は変えない。開始の記録に失敗していたときは、完了後に結果を一度に記録する

**中断の検出（E15）**: アプリが操作の途中で終了すると、その行は `running` のまま残る。次の起動時に、`running` の行をすべて `interrupted` に変え（`finished_at` は検出した時刻、`detail` は `interrupted`）、プロジェクトごとに `NeedsAttention`（理由 `interrupted-operation`）を通知する。画面が開く前の通知は届かないため、`project_status` の `interrupted_operation`（最も新しい中断の操作名）にも載せ、プロジェクト画面のヘッダーに最優先の「要対応」として表示し、その確認ボタンからダイアログで「操作前の状態に戻す」を案内する。利用者が同じプロジェクトで操作を成功させると、「中断」は「失敗」に変わり、案内は出なくなる（起動直後の自動実行では変えない）。

**保持期間**: 完了済み（`success` / `failure`）の行を、開始から「**自動保存の保持期間（設定 `snapshot_retention_days`: 30 / 90 / 365 日）と 90 日のうち長いほう**」を過ぎたものから削除する。つまり初期値では 90 日で、保持期間を 365 日にすると 365 日になる。復元点より先に記録が消えないよう、backup の保持期間（90 日）以上にしている。登録を外したプロジェクトの行は 90 日で削除する。`running` と `interrupted` の行は削除しない。整理は起動直後と 24 時間ごとの保守作業（6.2）で行う。

**復旧（E15）**: `recover_interrupted` が、中断された操作の直前の復元点へ作業フォルダを戻す。`reset --hard` と `checkout -f` は使わない。

1. 対象の操作は保存・取り込み系の `save`、`pull`、`push`、`resolve` だけ。それ以外が中断していれば、何も変更せず `not_recoverable` を返す（履歴から戻す時点を選んでもらう）。`push` は、拒否されたときに内部で取り込みを行うため、復元点は `pull` のものを探す
2. 復元点の選び方: その操作が**始まった時刻以降**に作られた、その操作の backup ref（`refs/hikae/backup/<操作名>/<時刻>`）のうち最新のものを探す。ジャーナルには完了しなかった操作の復元点が残らないため、操作名と開始時刻から探す。見つからなければ、何も変更せず `restore_point_not_found` を返す。見つかったら、同じ時刻のスナップショット（未保存の変更を含む）があればそれを、無ければ同じ `HEAD` から作られた直近のスナップショットを、それも無ければ backup ref（その時点の `HEAD`）を戻し先にする
3. 取り込みの途中で止まっていて `MERGE_HEAD` が残っているときは、先に `merge --abort` で取り込みを取り消す（復元点 `abort-merge` を作ってから行う）
4. 戻す前に、いまの状態の復元点を新たに作る。戻し方は「元に戻すの取り消し」と同じ `git restore --source=<復元点> --staged --worktree`。未追跡ファイルは消さない
5. 実行は直列キューとジャーナル（操作名 `recover`）を通す。成功すると中断の印を解除する

設計の「続きを行う」（取り込みを再開する選択）と、`MERGE_HEAD` や `index.lock` の検査による他のツールの中断との区別は**未実装**です。いまの案内は「操作前の状態に戻す」だけです。

### 6.4 そのほかの保証

- **未追跡ファイルを復元不能な形で削除しない**（安全上の不変条件 6）: アプリが作業フォルダからファイルを消すのは、次の 2 つの場合だけ。(1) 「元に戻す」で、その時点に存在しない**追跡ファイル**を対象にした場合（直前にスナップショットがある）。(2) 利用者が明示的に新規ファイルの「元に戻す（作成しない）」を選んだ場合に限り、**未追跡ファイル 1 件**を、直前のスナップショットに内容を残したうえで、**OS のごみ箱へ移す**（4.2）。(2) でも完全な削除は行わず、復元点に入らない大きさのファイル、追跡済み・保存対象外のファイル、フォルダ・リンクは対象にしない。追跡解除は `git rm --cached` のみ
  - **不変条件を改訂した理由**: 以前の不変条件は「未追跡ファイルを削除しない」だった。しかし、保存前の新規ファイル（誤ってコピーしたファイルなど）は、戻す先の版が無いため、利用者が「作らなかったことにする」手段が無く、アプリの外（ファイルマネージャー）で消すしかなかった。そのため、利用者が明示的に選んだ 1 件に限り、(a) 復元点にバイト単位で一致する内容があること、(b) ごみ箱に移ること（完全な削除ではない）、(c) 復元点に入らない大きさは対象外、の 3 つを満たす場合に例外を設けた。復元不能な削除は引き続き行わない
- **追跡解除でローカルを消さない**: 4.8 の「保存対象から外す」は `--cached` 固定。他 PC での削除は 4.3 手順8で書き戻す
- **アップロード済みの履歴は変えない**: 公開側の ref を書き換える操作は存在しない
- **復元 UI**: 設定の「詳細」に「自動保存から復元」画面を置き、スナップショットを時刻順に一覧して任意の時点のファイルを取り出せるようにする（最後の砦）。専用の画面は**未実装**で、設定の詳細設定は空。いまは履歴のタイムラインに自動保存（`refs/hikae/snapshots/`）が並ぶ
- **自動保存をクラウドにも控える**（Phase 3、初期値オフ）: `refs/<app>/snapshots/*` を明示指定で push する。容量を使うため既定では行わない

### 7.2 設定の保存と反映状況（実装）

**保存**: アプリ内の SQLite（`core-store`）に、全体の設定を `settings`（キーと JSON 値）、プロジェクト別の上書きを `project_settings`（プロジェクト ID・キー・JSON 値）として保存します（9.1）。9.1 の当初案の「OS の設定ディレクトリの JSON」は使いません。

- 保存されていないキーは既定値になる。保存済みの値が壊れていた（JSON として読めない、型や選択肢に合わない）場合も、そのキーだけ既定値に戻して読み、設定の破損でアプリを使えなくしない。未知のキーは無視する
- 更新は、指定した項目だけを書き換える部分更新。保存前に検証し、範囲・選択肢にない値は保存せず `invalid_settings` で拒否する。数値の項目は、画面では「選択肢 + カスタム」で、範囲内の任意の整数を設定できる（`core-store` の `settings.rs` の定数。画面の `number-input.ts` と一致させる）: 取り込み間隔 0（オフ）または 1〜1440 分、自動保存の静止時間 10〜3600 秒、保持期間 7〜730 日、警告閾値 1〜100MB。範囲外の入力は、画面が入力欄の下に1行の注記を出して保存しない。選択肢だけの項目: アップロード待ちの通知 0 / 1 / 24 時間、自動保存の容量上限 0 / 1 / 2 / 5 倍（`0` は「オフ」または「上限なし」）
- 実際に使う設定は、全体の設定にプロジェクト別の上書きを重ねたもの。プロジェクト別に上書きできるのは次の 14 項目だけで、それ以外を上書きしようとすると拒否する: `pull_on_startup`、`pull_interval_minutes`、`save_before_pull`、`conflict_mode`、`auto_push_after_save`、`push_reminder_hours`、`auto_snapshot_enabled`、`auto_snapshot_delay_secs`、`snapshot_retention_days`、`memo_suggestion`、`auto_save_after_restore`、`large_file_warn_mb`、`show_snapshots_in_timeline`、`open_action`。AI、git 実行ファイル、詳細設定（7.1）の項目は、アプリ全体でのみ設定する
- 設計書の項目に加えて、初回設定（ログインと最初のプロジェクトの案内）を完了したかを `onboarded` として保存する
- 旧形式（`projects.config` の JSON）の上書きは、マイグレーション v4 で有効な値だけを `project_settings` へ移した。列自体は残るが、設定の読み書きには使わない
- 設定画面（S5）は、いまは「一般」「取り込み」「アップロード」「自動保存」の 4 タブで、各タブの項目は即時保存（保存ボタンは無い。選択肢は選んだとき、カスタムの数値は入力欄から外れたとき・Enter を押したときに保存する）。他の画面から `?tab=auto_save` のように開くタブを指定できる。プロジェクトの画面から開いたときは、プロジェクト別の上書きにも切り替えられる。詳細設定（7.1）の折りたたみは空で、項目の画面は未実装。**画面に出すのは、バックエンドが実際に読んでいる設定だけ**（下の反映状況で「反映済み」のもの。`pull_on_startup`、`pull_interval_minutes`、`save_before_pull`、`auto_push_after_save`、`auto_snapshot_enabled`、`auto_snapshot_delay_secs`、`snapshot_retention_days`、`large_file_warn_mb`、`show_snapshots_in_timeline`）。保存のみの設定は、保存スキーマ・DB・検証には残したまま画面から外している。対応する機能を実装した時点で、画面に戻す

## 8. 技術スタック比較と推奨構成

推奨は「Tauri 2 + SvelteKit（Svelte 5）+ Master CSS（rc）、Git 操作は同梱の git CLI、LLM は llama.cpp の `llama-server` をサイドカー起動」です。Git の挙動を本家と完全に一致させることと、LLM やファイル監視の不具合でアプリ本体が落ちないことを優先しました。

### 8.1 Git 操作層の比較

| 候補 | 機能網羅 | 速度 | 認証 | 配布 | 判定 |
| --- | --- | --- | --- | --- | --- |
| git CLI（同梱） | 完全。merge、競合ステージ、LFS も本家どおり | 1回の起動に数十 ms（Windows で遅め）。`-z` / `--porcelain=v2` の解析が必要 | 自作 credential helper でトークンを渡せる | Windows は MinGit、macOS は自前ビルドを同梱（数十 MB。実装状況は 8.2 と 13.3） | **採用** |
| libgit2（git2-rs） | 基本操作は可。merge 周りやフック、LFS は非対応または挙動差あり | プロセス起動なしで高速 | コールバックで実装可能 | ライブラリ静的リンクのみ | 不採用（挙動差が安全設計の前提を崩す） |
| gitoxide（gix） | 読み取り系は成熟。書き込み・push は発展途上 | 高速 | 実装途上 | Pure Rust で配布が楽 | Phase 3 で読み取り高速化に検討 |
| isomorphic-git | 限定的。大きいリポジトリで遅い | 遅い | HTTP のみ | JS のみで完結 | 不採用 |

補足: git は GPLv2 のため、同梱時はライセンス文書と入手先を明示します。アプリ本体は別プロセスとして呼び出すだけなので、アプリのライセンスには影響しません。

**ツールチェーンと設定の注意**（Phase 0 で判明）:

- Rust は 1.99 以上が必要（specta rc.25 が 1.89 でコンパイルできず、tauri 2.12 は 1.90 以上を要求）。`src-tauri/rust-toolchain.toml` で固定する
- Master CSS rc の設定は `master.css.ts` ではなく CSS の `@theme` で書く。トークン名は名前空間付きの CSS 変数になる（例: `--color-bg`、`--spacing-3`）。使われた変数だけが出力される
- SvelteKit 3 では `svelte.config.js` が廃止され設定は Vite 側に書く。`$lib` は `#lib`（`package.json` の `imports`）に変わった
- Windows では、tauri にリンクするテスト実行ファイルが起動しない（`STATUS_ENTRYPOINT_NOT_FOUND`）。型生成は別 bin（`export-bindings`）で行う

**認証とリモートの扱い**（実装）:

- 方式は GitHub OAuth App の Device Flow（GitHub App ではない）。GitHub 側の設定は「Enable Device Flow」をオン、「Expire user access tokens」（有効期限つきのトークン）をオフ、Client secret は使わない。これらは GitHub 上の設定で、コードからは確認できない（運用者の申告）。コード側は、期限なしのアクセストークンを前提に、リフレッシュトークンの処理を持たない
- `client_id` は秘密ではない公開情報として、ソースに既定値を埋め込む（配布版の利用者は環境変数を設定できないため）。解決の優先順位は、実行時の環境変数 `HIKAE_GITHUB_CLIENT_ID` → ビルド時の同名の環境変数 → 埋め込みの既定値。空の値は無視する。Client secret はソースにもリポジトリにも置かない
- スコープは `repo`（非公開リポジトリの読み書き）と `read:org`（所属 Org の一覧）で固定
- ログインの流れ: `start_login` が確認コードと確認ページの URL を返す（`device_code` はバックエンド内部にだけ保持し、画面には渡さない）→ `open_login_page` が既定のブラウザで確認ページを開く（開くのは進行中のログインが保持する URL が `https://github.com/login/device` と完全に一致するときだけ）→ `wait_login` が許可されるまでポーリングする（`authorization_pending` は待機、`slow_down` は間隔を延ばす、期限切れ・拒否・中断は専用の結果で返す）。許可されたトークンは、呼び出し側がキーチェーンへ保存する
- トークンの保管は OS のキーチェーン（Windows の資格情報マネージャー、macOS の Keychain）だけ。ファイル、ログ、操作ジャーナル、イベント、画面に返す型には出さない。トークンと `device_code` の `Debug` / `Display` は伏せ字にする。ログアウトはキーチェーンのトークンを削除するだけで、GitHub 側の許可の取り消しは行わない
- git への受け渡しは、アプリ自身を credential helper として使う。`clone` / `fetch` / `push` / `ls-remote` の実行時だけ、`-c credential.helper=`（既存の helper の無効化）に続けて `-c credential.helper=!'<アプリ>' credential` を付ける。git が `<アプリ> credential get` を呼ぶと、アプリは画面を起動せずに応答して終了する。応答するのは `https` で `github.com` 宛ての `get` だけで（ユーザー名 `x-access-token`、パスワードはトークン）、それ以外のホスト・操作（`store`、`erase`）には何も出力しない。トークンを URL やコマンドライン引数には載せない。実行ファイルのパスに引用符や制御文字が含まれるときは helper を設定せず、認証なしで実行して認証エラーとして失敗させる。ユーザーのグローバル git 設定には書き込まない（6.1）
- リモートは GitHub の `origin` のみ。取得先は `https://github.com/<owner>/<name>.git` に固定する（4.6）。トークンが失効・取り消しされると API は 401 を返し、セッション情報は「再認証が必要」になる（E01）。オフラインや GitHub 側の障害のときはログイン状態を変えず、ユーザー情報だけを空にして返す
- 署名に使うユーザー情報（数値 ID とログイン名）はメモリ上に控え、保存のたびに通信しない。トークンは含めない
- **未確認**: Device Flow の実認証（ブラウザでの手動承認）と、実際の GitHub でのリポジトリ作成（`POST /user/repos`、`POST /orgs/{org}/repos`）。リポジトリの作成は、モックの HTTP サーバーとローカルの bare リポジトリを使うテストだけで確認している

### 8.3 モジュール分割

Rust 側は Cargo workspace で機能ごとに crate を分け、Tauri 層（`app`）からのみ組み合わせます。各 crate は Tauri に依存しないため、単体テストと CLI での動作確認が可能です。

| crate / ディレクトリ | 責務 | 依存先 |
| --- | --- | --- |
| `core-git` | `GitRunner`（許可リスト、環境変数、タイムアウト）、出力パーサ | なし |
| `core-safety` | スナップショット、バックアップ ref、復元点の間引き | core-git |
| `core-ops` | 保存、元に戻す、取り込み、アップロード、ぶつかり解消、除外設定の各ユースケース | core-git, core-safety |
| `core-watch` | ファイル監視（`ProjectWatcher`）と、無視するパスの判定・変更のまとめ方・自動保存の静止判定（`SnapshotPlanner`。時刻を引数で受け取る純関数）、取り込み・アップロードの実行計画（起動時・定期・再試行）、保守タイマー | core-safety |
| `core-github` | Device Flow、REST API、keyring、credential helper | なし |
| `core-preview` | 種別判定、テキスト／画像／docx／xlsx 抽出、拡張機能ホスト（雛形のみ） | なし |
| `core-llm` | モデル管理（DL・検証・削除）、サイドカー制御、Ollama 接続、プロンプト生成（雛形のみ） | core-preview |
| `core-store` | SQLite、設定、プロジェクト登録、操作ジャーナル、プロジェクト単位のロック（`ProjectLocks`） | なし |
| `app` | Tauri コマンド・イベント、スケジューラ、プロジェクト単位の操作キュー | 上記すべて |
| `src/lib/features/*` | projects, changes, history, compare, conflict, settings, ai, extensions | 生成された TS バインディング |

```text
UI（WebView・SvelteKit） ←postMessage→ 拡張 renderer（sandbox iframe）
        │
app（Tauri コマンド・イベント／操作キュー（直列）／スケジューラ）
   │          │            │             │              │            │
core-ops   core-watch   core-github   core-preview    core-llm     core-store
   └────┬─────┘            │             │              │            │
   core-safety           GitHub API    WASM 抽出器     llama-server  SQLite
        │                  │            (wasmtime)     または Ollama
     core-git              │
        │                  │
  git CLI（同梱）            │
        └──────┬───────────┘
      GitHub 上のリポジトリ
```

UI と拡張 renderer は Rust 層を介さずに Git やファイルへ触れられず、状態変更はすべて操作キューから core-safety を経て git CLI に届きます。

**操作キュー**: 同一プロジェクトへの状態変更は `app` 層の直列キューで1件ずつ実行します。自動取り込みと手動保存が同時に走って `index.lock` が衝突する事態を、設計上発生させないためです。読み取り（状態表示、履歴、比較）はキューを通さず並列に実行します。

実装: プロジェクト ID ごとのロック（`core-store` の `ProjectLocks`。ID ごとに 1 つの `Mutex`）を、`app` の `run_exclusive` が**ブロッキング用スレッドの内側**で取ってから処理を実行します。ロックを外側で取ると、クロージャがすぐ戻ってロックが本体の実行前に解放され、直列にならないためです（Phase 1 の実装中に見つかった不具合。13.3）。保存・取り込み・アップロード・元に戻す・ぶつかり解消・ファイル追加・復旧は共通の `run_op` を通り、直列キューの内側で、ジャーナルの記録（6.3）と UI へのイベント通知まで行います。スケジューラの自動実行も同じ `run_op` を通ります。

## 9. データモデル・状態管理

真実の情報源は常に Git リポジトリと Rust 側です。フロントエンドは表示用のキャッシュのみを持ち、バックエンドからのイベントでキャッシュを無効化して再取得します。履歴やファイル内容を SQLite に複製しないことで、外部ツールで操作された場合も表示が食い違いません。

### 9.1 永続データ

| 保存先 | 内容 | 主な項目 |
| --- | --- | --- |
| SQLite `settings` / `project_settings` | アプリ全体の設定と、プロジェクト別の上書き（7.2） | キーと JSON 値。UI 言語は日本語のみで保存項目なし。ウィンドウ状態の保存は未実装 |
| SQLite `projects` | 登録プロジェクト | id、パス（一意）、表示名、remote URL、所有者（個人のログイン名）、既定ブランチ、最終表示日時、最初の保存の OID（`initial_commit`）。`config`（旧形式の上書き JSON）は残るが未使用 |
| SQLite `journal` | 操作ジャーナル | 6.3 |
| SQLite `snapshots`、`skip_worktree`、`llm_models`、`message_cache`、`extensions` | 表は作成済みだが、**読み書きする処理は未実装**（Phase 2 以降の用途） | 当初案の項目のまま。スナップショットの一覧は、現状は ref から直接読んでいる（`for-each-ref`） |
| `.git/hikae/tmp/` | スナップショット作成用の一時インデックス（処理後に削除） | 6.2 |
| OS キーチェーン | GitHub トークン | — |

SQLite のファイルは、Tauri の `app_data_dir` 配下の `hikae.db` です。外部キー制約は有効にしていません（`ON DELETE CASCADE` に頼らず、プロジェクトの登録を外すときは `project_settings` を明示的に削除します）。`.git/<app>/journal.json` と `.git/<app>/project.json` は使いません（ジャーナルは SQLite へ移し、フォルダ移動後の再紐づけには `projects.initial_commit` を使います）。

**マイグレーション**（`PRAGMA user_version` で管理。起動時に未適用のものを順に実行）:

| 版 | 内容 |
| --- | --- |
| v1 | 初期スキーマ。`projects`、`snapshots`、`skip_worktree`、`llm_models`、`message_cache`、`extensions` を作成 |
| v2 | 操作ジャーナル `journal` と索引 `idx_journal_project_started` を作成（外部キーなし） |
| v3 | `projects` に `initial_commit` 列を追加。保存先 URL が無いプロジェクトでも、フォルダの付け替え（`relocate_project`）時に同じ履歴か照合できるようにする。プロジェクトの登録時と最初の保存の後に記録し、記録済みなら上書きしない |

### 9.2 プロジェクトの状態

ヘッダーの1行表示（2.2）は、次の値から算出します。

| 値 | 取得元 | 更新契機 |
| --- | --- | --- |
| 未保存の変更（件数・一覧） | `git status --porcelain=v2 -z` | ファイル監視イベント（300ms で間引き。`files-changed`）。監視が動いていないときだけ、フォールバックとして 30 秒ごと |
| アップロード待ち／取り込み待ち | `git rev-list --left-right --count` | 保存、fetch、push の完了 |
| 実行中の操作 | 操作キュー | 操作の開始・進捗・終了イベント |
| ネットワーク状態 | 直近の fetch / API 結果 | 失敗・成功時 |
| 要対応事項 | ジャーナル、未解消のぶつかり（`MERGE_HEAD` の検査は未実装） | 起動時、操作終了時 |

操作中の状態遷移は次のとおりです。`待機` 以外の状態では状態変更系のボタンを無効化し、操作キューに積まれた件数を表示します。

| 現在の状態 | イベント | 次の状態 |
| --- | --- | --- |
| 待機 | 保存 / 元に戻す / 取り込み / アップロード開始 | 実行中（操作名） |
| 実行中 | 成功 | 待機 |
| 実行中（取り込み） | 競合検出 | ぶつかり解消待ち |
| ぶつかり解消待ち | 解消して保存 / あとで（merge 中止） | 待機 |
| 実行中 | 失敗 | 復元点へ戻したうえで待機（エラー表示） |
| 任意 | アプリ異常終了 → 再起動 | 要対応（E15） |

実装の補足:

- 「実行中 → 失敗」で復元点へ**自動で戻す処理は実装していない**。失敗した操作は、エラーを返して終わる（復元点は残るため、履歴からの操作や E15 の復旧で戻せる）。当初の設計（4章冒頭）との差
- 未保存の変更の更新契機は、ファイル監視（Phase 1 に前倒しして実装）のイベント `files-changed` と、操作の完了イベント。画面は `files-changed` を受けたら変更一覧とメモの案だけを取り直す（履歴・一覧など git を多く呼ぶ取得は動かさない）。ファイル監視が動いている間（`project_status` の `watching`）は、画面は変更一覧を定期的に取り直さない。監視を開始できない・途中で失敗したときは、60 秒後に開始をやり直し、そのあいだはフォールバックとして 30 秒間隔で取り直す（これまでの 5 秒間隔のポーリングは廃止）。ウィンドウに戻ったときは常に取り直す。ブラウザ単体（モック）では取り直さない。操作の開始・終了は `op_progress` / `op_finished`、状態の変化は `status_changed` で通知する
- ファイル監視の開始・停止は、スケジューラの巡回（登録・削除・付け替え・設定変更の直後と、最長 30 秒ごと）で、フォルダが見つかるプロジェクト（E11 でないもの）に合わせる。監視を始めるとき・止めたときは `status_changed` で `watching` を取り直させる
- 「待機以外ではボタンを無効化し、操作キューに積まれた件数を表示する」ことは未確認（キュー内の件数をイベントで通知する処理は確認できなかった）

- **コマンド**（UI → Rust、tauri-specta で `src/lib/bindings.ts` を型生成。`app/src/lib.rs` の `specta_builder` に登録した 40 個）:
  - プロジェクト: `list_projects`、`add_project`、`remove_project`、`relocate_project`、`project_status`
  - 変更・保存: `list_changes`、`suggest_memo`、`save`、`save_with_size_choice`、`add_files`
  - 履歴・比較: `list_history`、`list_point_changes`、`list_files_at`、`diff`

## 10. ローカル LLM 設計

LLM が要約できるのは「アプリが取り出した情報」であり、バイナリそのものではありません。docx・xlsx は抽出テキストの差分を渡せば 3〜4B 級で内容に触れた要約ができ、画像は視覚対応モデル（VLM）が必要で、ノート PC では実用の下限付近になります。そのため「AI に渡す範囲」を段階として選ばせ、段階ごとに必要なモデルと PC の条件を表示します。

### 10.1 VS Code との違い

VS Code（GitHub Copilot）のメッセージ生成が自然なのは、クラウド上の大規模モデルを使っているためです。ローカルで同等の自然さを得るには 7B 級以上とメモリ 16GB 程度が目安になり、一般的なノート PC を対象に含める本件の前提とは両立しません。本アプリでは、小型モデルでも品質が安定するよう、入力を構造化し出力形式を制約します（10.4）。

### 10.2 段階と必要条件

下表のサイズ・速度は 4bit 量子化を前提とした目安で、実機での計測により確定させます。

| 段階 | AI に渡す範囲 | 生成例 | モデル規模 | DL 容量の目安 | 推奨メモリ | CPU のみでの応答の目安 |
| --- | --- | --- | --- | --- | --- | --- |
| 0 | なし（ルールのみ） | 第3章.docx を更新、ほか2件 | 不要 | 0 | — | 即時 |
| 1 | ファイル名・変更種別・件数 | 第3章の更新と図の追加 | 1〜2B | 約 1〜1.5GB | 8GB | 数秒 |
| 2 | 上記＋テキスト差分＋docx/xlsx の抽出差分 | 第3章の実験回数を5回に修正し、追加実験の結果を追記 | 3〜4B | 約 2〜3GB | 8GB（16GB 推奨） | 10〜30秒 |
| 3 | 上記＋画像（変更前後） | 図4に棒グラフを追加 | 3〜4B 級の VLM | 約 3〜5GB | 16GB | 30秒以上 |
| 4 | 段階2と同じ範囲を高品質に | 段階2より自然な文、複数行の要約 | 7〜9B | 約 5〜6GB | 16GB 以上（GPU または Apple Silicon 推奨） | GPU なしでは実用外 |

- 推奨は段階2です。docx・xlsx・テキストの変更内容に触れられ、8GB の PC でも動作します。段階1はルールベースとの差が小さく、導入の価値が限定的です
- 段階3は Phase 3 とし、画像は「追加・削除・差し替え」の事実だけならルールで十分なことを UI で示します
- PDF・psd・動画などは、抽出器がない限りどの段階でもファイル名と種別の情報のみになります。11章の拡張機能が抽出器を提供すれば、段階2の入力に加わります
- 具体的なモデル名は実装時点で日本語の要約品質を評価して決めます。カタログを外部 JSON として配信し、アプリ更新なしで差し替えられるようにします

### 10.3 ルールベース生成（段階0、常に動作）

| 条件 | 生成文 |
| --- | --- |
| 1ファイルの変更 | `<ファイル名> を更新` / `を追加` / `を削除` / `<旧名> を <新名> に名前変更` |
| 同種のファイルのみ複数 | `画像を3件追加`、`文書を2件更新` |
| 混在 | 最も変更量の大きいファイル名 ＋ `ほか n 件` |
| 元に戻す操作 | `<日時> の状態に戻しました（n 件）` |
| ぶつかり解消 | `2台の変更をまとめました` |

### 10.4 生成の仕組み

1. 保存欄には常にルールベースの文を先に入れる。LLM の結果は「✨ 提案」として横に並べ、採用はユーザーが押したときのみ。保存操作は LLM を待たない
2. 入力の構造化: 変更ファイルを「種別・ファイル名・変更量」の表として渡し、差分本文はファイルごとに上限を設けて切り詰める（全体で約 2,000 トークン）
3. 出力の制約: `llama-server` の JSON Schema 制約（Ollama は `format` 指定）で `{ "summary": "50字以内", "details": ["…"] }` の形を強制し、小型モデルの書式崩れを防ぐ
4. タイムアウト（段階2で 30秒）・不正出力・プロセス異常終了時はルールベースのまま何も表示しない（E19 は設定画面でのみ表示）
5. 同じ差分（ツリーの OID）に対する結果は `message_cache` から返す

### 10.5 モデル管理と実行

- **導入**: 設定の AI タブで段階を選ぶ → PC のメモリ・空き容量を検査し、条件を満たさない段階は理由つきで灰色表示 → DL（再開対応、SHA-256 検証）→ アプリのデータフォルダに配置
- **起動と解放**: 生成が必要になった時点で `llama-server` を起動し、5分間使わなければ終了してメモリを解放する
- **GPU**: macOS は Metal、Windows は CPU 版を既定とし、Vulkan 版を詳細設定で選べるようにする（GPU ドライバ依存の不具合を既定値で踏まないため）
- **Ollama への切替**（詳細設定）: 接続先 URL（初期値 `http://localhost:11434`）を指定し、Ollama 側のモデル一覧から選ぶ。通信は OpenAI 互換 API で共通化しているため、`core-llm` 内の分岐は接続先とモデル一覧の取得のみ
- **プライバシー**: 内蔵・Ollama のいずれも PC 内で完結し、ファイル内容は外部へ送信しない。Ollama の接続先に外部ホストが指定された場合は警告を出す

## 11. プレビュー拡張機能の設計

拡張機能は「表示を担う UI（サンドボックス iframe）」と「内容を取り出す抽出器（WASM）」の2種類に分け、どちらもファイルやネットワークに直接触れられない形にします。当面は自作のみですが、最初から第三者向けと同じ境界で作れば、公開時に作り直しが要りません。組み込みのプレビュー（テキスト、画像、docx、xlsx）も同じ API で実装し、API の不足を自分で先に踏みます。

### 11.1 構成

| 種類 | 役割 | 実行環境 | 入力 | 出力 | 制限 |
| --- | --- | --- | --- | --- | --- |
| 表示（renderer） | 1時点の表示、2時点の比較表示 | `sandbox="allow-scripts"` の iframe（同一オリジン不可）、`ext://<id>/` から配信 | `postMessage` で受け取るファイルのバイト列と種別 | 描画のみ | CSP で `connect-src 'none'`。Tauri の IPC に届かない |
| 抽出器（extractor） | 比較用テキスト・LLM 入力の生成 | Rust 側の wasmtime（WASI、ファイル・ネットワークなし） | ファイルのバイト列 | テキストまたは構造化 JSON（段落、セル、ページ） | メモリ 256MB、実行 10秒 |

抽出器を WASM にする理由は、作者が Rust・Go・C など任意の言語で書けること、ネイティブコードを配布させずに済むこと、異常終了してもアプリを巻き込まないことです。

### 11.2 マニフェスト

```json
{
  "id": "example.pdf-preview",
  "name": "PDF プレビュー",
  "version": "1.0.0",
  "apiVersion": "1",
  "contributes": {
    "renderers": [
      { "fileTypes": [".pdf"], "modes": ["view", "compare"], "entry": "ui/index.html" }
    ],
    "extractors": [
      { "fileTypes": [".pdf"], "output": "paragraphs", "entry": "extract.wasm" }
    ]
  },
  "permissions": []
}
```

- `modes` に `compare` がない場合、アプリが `view` を2つ並べて比較画面を作る
- 抽出器の `output` が `paragraphs` / `cells` / `pages` のいずれかなら、アプリ側の行差分・セル差分ビューと LLM 入力（10章 段階2）にそのまま使える
- `permissions` は将来の拡張用に予約（例: 外部フォント読み込み）。初期は空のみ受け付ける

### 11.3 段階的な公開

| フェーズ | 内容 |
| --- | --- |
| Phase 2 | 組み込みプレビューを拡張 API 上で実装（API は非公開） |
| Phase 3 | フォルダまたは zip から手動インストール（開発者モード）。雛形を生成する CLI と型定義パッケージを用意 |
| Phase 4 | GitHub リポジトリ上の索引 JSON を拡張機能一覧として表示。ed25519 署名の検証、権限の事前表示、API バージョン N と N-1 の互換維持 |

### 11.4 採用しなかった案

- **拡張の JS をメイン WebView で実行**: Tauri の IPC に到達でき、ファイル削除や push も呼べるため不採用
- **Node.js ベース（VS Code 型）**: Tauri には Node が無く、同梱すると配布サイズの利点が消えるため不採用
- **ネイティブの動的ライブラリ**: OS・CPU ごとのビルドが必要で、異常時にアプリごと落ちるため不採用

## 13. リスクと判断が必要な論点

最大のリスクは、Git がファイルを「バックアップ」ではなく「ソースコード」として扱う既定動作（改行変換、巨大ファイルの扱い、追跡解除時の削除）です。これらは既定値を明示的に上書きして封じます。

### 13.1 設計上のリスク

| リスク | 影響 | 対策 |
| --- | --- | --- |
| 改行コードの自動変換 | Windows と macOS の間でファイル内容が書き換わり、「変更していないのに変更あり」が出る | リポジトリ作成時に `core.autocrlf=false` を設定し、バイト列をそのまま保存する（バックアップ用途として正しい挙動） |
| 日本語ファイル名 | macOS の NFD 正規化で別ファイル扱い、出力の引用符エスケープで解析失敗 | `core.precomposeUnicode=true`、出力は常に `-z` 形式で解析 |
| 大きいファイルでリポジトリが肥大化 | GitHub の制限、clone の長時間化。一度保存すると履歴から消せない | 保存前の検査（E07〜E09）、Phase 4 まで LFS は入れない |
| Office の一時ファイル（`~$*.docx` 等）の混入 | 不要な変更・削除が履歴に残る | 初期の .gitignore テンプレートに OS・Office の一時ファイルを含める |
| クラウド同期フォルダ（OneDrive、iCloud）上のプロジェクト | 同期ソフトが `.git` を書き換え、リポジトリが破損する | 登録時にパスを検査して警告。E10 の復旧手順を用意 |
| ファイル監視の負荷 | 大きなフォルダで CPU 使用率が上がる | `.git` と除外対象を監視から外す。静止判定で間引く（実装済み。13.3） |
| skip-worktree の限界（4.8） | 取り込みで該当ファイルが更新されると merge が失敗する | 取り込み前に一時解除 → 内容退避 → 再設定、の手順を `core-ops` に実装 |
| Org の OAuth アクセス制限 | Org のリポジトリにアクセスできない | E02 の文言と、管理者向け説明文のコピー機能 |
| 署名・公証のコスト | 年間費用と手続き | Phase 0 で手続きを開始。未署名の開発版は自分用に限定 |
| WebView の差異 | Windows と macOS で表示や D&D の挙動が異なる | 両 OS での E2E テストを Phase 1 の CI に含める |

- **Master CSS が rc 版である点**: 採用時点の rc 版にバージョンを固定して運用し、正式版への追従は必須としない（lockfile で固定）
